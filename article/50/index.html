# 从 SPA 到 SSG

传统 Vue SPA 首次访问时，服务器通常只返回一个 HTML 根节点：

HTML 
<div id="app"></div>

浏览器随后还需要：

  1. 下载 js；
  2. 执行 js；
  3. 创建 Vue 应用；
  4. 请求页面所需的数据；
  5. 根据数据生成实际 DOM。

在 js 执行和数据请求完成之前，页面可能只显示空白或加载状态，且对于博客来说，这种方式存在两个比较明显的问题：

  • SEO不友好：搜索引擎首次拿到的 HTML 缺少文章内容，对 SEO 不够友好；
  • 白屏：页面需要等待 JavaScript 和接口请求完成，首屏内容出现得较晚。

因此，我在博客中引入了 vite-ssg，在项目构建阶段提前生成静态 HTML，构建完成后，可以得到类似下面的文件：

text 
dist/
├─ index.html
├─ about/
│  └─ index.html
└─ article/
   ├─ 1/
   │  └─ index.html
   ├─ 2/
   │  └─ index.html
   └─ ...

这样后续访问博客时，服务器直接返回渲染后的静态HTML，此时即使 js 尚未完成加载，用户和搜索引擎也能看到主要内容。

# vite-ssg 的局限：静态 HTML 的数据可能过期

vite-ssg 生成的是构建时的数据快照。

假设网站在 7 月 1 日执行构建，首页静态 HTML 包含当时最新的 10 篇文章。7 月 2 日发布了一篇新文章，但没有重新构建前端，那么已经部署的 index.html 并不会自动更新。

用户访问时，可能经历下面的过程：

text 
返回构建时的静态 HTML
    ↓
先显示构建时的旧文章
    ↓
下载并执行客户端 JavaScript
    ↓
Vue 接管页面
    ↓
客户端请求最新文章
    ↓
更新为最新数据

这是引入 vite-ssg 后的正常流程：

  • 先用旧数据保证首屏立即有内容；
  • 再通过客户端请求更新为最新数据。

旧数据并不是问题，只要客户端最终能够重新请求和更新，那么此次首页数据为什么没有更新？bug 是如何产生的呢？

# Bug 是如何产生的

initialState 文档：https://github.com/antfu-collective/vite-ssg#initial-state

查看了 codex 更改的代码，发现首页的数据没有更新，便在于 codex 自动进行了脑补，使用 initialState 将数据序列化到首页的HTML，又通过 loaded 判断阻止客户端重新请求，导致后续不会重新获取数据，详情如下：

首页在构建阶段通过 onServerPrefetch() 请求文章：

js 
onServerPrefetch(async () => {
  await loadPage();
});

请求成功后，loadPage 会将首页数据和 loaded 状态写入 Pinia：

js 
articles.value = res.data.articles;
page.value = res.data.page;
total.value = res.data.total;
loaded.value = true;

随后，vite-ssg 通过 initialState 将 Pinia 状态序列化到静态 HTML：

js 
if (import.meta.env.SSR) {
  onSSRAppRendered(() => {
    initialState.pinia = pinia.state.value;
  });
} else {
  pinia.state.value = initialState.pinia || {};
}

序列化的结果，将输入写入首页的静态 HTML：

html 
<!DOCTYPE html>
<html lang="en">
<head>
  <title>Tilex Blog</title>
</head>
<body>
  ……
</body>
<script>window.__INITIAL_STATE__="{\"pinia\":{\"home\":{\"loaded": true,\"articles\":[{\"id\":49,\"title\":\"雨天上班.md\",\"preview\":\"\u003E TAG: DAILY\\n\\n# 雨天上班\\n\\n![IMG_20260728_192947_1](https:\u002F\u002Foss.tilex.
……
</html>

浏览器访问首页时，会恢复构建阶段的 Pinia 状态，其中包括：

js 
loaded.value === true;

但客户端在处理时，却增加了 loaded 判断：

vue 
onMounted(() => {
  if (!loaded.value) { // bug 产生的核心
    loadPage();
  }
});

此时 loaded 为 true，客户端请求会被直接跳过

完整过程如下：

text 
构建阶段请求文章
→ loaded = true
→ Pinia 状态写入 initialState
→ 客户端恢复 loaded = true
→ onMounted 跳过请求
→ 首页一直显示构建数据（旧数据）

修复很简单，直接移除 loaded 的判断即可

vue 
onMounted(() => {
    loadPage();
});

但，还需要 initialState 吗？此时 initialState 似乎没有起到任何作用，甚至构建生成的HTML文件体积更大：initialState 会将序列化的数据写入静态HTML

# initialState 使用的权衡

initialState 的主要作用是把构建阶段的数据传递给客户端，让客户端第一次渲染与静态 HTML 保持一致，从而稳定完成水合。

使用 initialState 后，首页流程为：

  • 返回包首页构建阶段的静态 HTML，包括 initialState 序列化后的数据；
  • 客户端通过数据，直接恢复<u>构建时</u>的 Pinia 状态；
  • Vue 使用相同状态完成水合；
  • 水合后请求最新数据；
  • Vue 根据新旧数据差异更新页面。

它的代价是静态 HTML 中同时存在渲染后的 DOM 和序列化状态，产生双份载荷。数据越多，HTML 体积和解析成本越明显。

因此，是否使用 initialState 需要根据页面情况权衡：

  • 数据较小，并且希望避免水合不一致和内容闪烁（新旧数据的交接），可以使用；
  • 数据很大，且能够接受静态内容在客户端重新渲染，可以考虑移除；
  • 也可以只序列化水合必需字段，减少载荷。

当然，我的选择是移除 initialState，保持构建时静态HTML的简洁

# 对 AI 修改代码的反思

使用 AI 修改项目时，往往存在许多<u>没有说明、留白的地方</u>，这些地方甚至不在你的认知范围内，此时 AI 对于这些地方往往会自动“脑补”，如此次bug，我之前甚至并没有接触过 initialState ，对它并不了解 ，但审核时却遗漏了
