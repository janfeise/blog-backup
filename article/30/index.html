git多人合作分支学习

阅读时间约 11 分钟 · 字数 2010

# Git 多人协作分支规范（main / dev / 业务分支）

在团队协作中，一般会长期保留两个核心分支：

  • main：生产环境的稳定版本
  • dev：开发环境的集成分支

后续所有业务开发均在独立的业务分支完成，最终合并进 dev，验证无误后再同步到 main

# 分支结构示意图

# 本地创建业务分支并推送到远程

# 1. 创建本地分支

text 
git checkout -b 分支名

# 2. 推送到远程并建立关联

text 
git push -u origin 分支名

-u 作用：设置「上游分支」，以后该分支可直接 git push / git pull

# 3. 查看远程分支是否创建成功

text 
git branch -r

-r（remote）：列出所有远程分支

# 推送当前分支的更改

  1. git add .
  2. git commit -m “提交备注”

git push 的作用是：

只会将当前所在分支的提交推送到与之关联的远程分支

如果你在 feature-login 分支：

text 
git push

只会更新 origin/feature-login，不会影响其它分支

切换分支：

text 
git checkout 分支名

# 合并流程：业务分支 → dev 分支

业务分支开发完成后，需要合并到 dev常见有两种方式：

# 方式 A：通过 GitHub / GitLab 提 PR（推荐）

创建 Pull Request / Merge Request：

text 
source: feature-login
target: dev

由团队成员 review，确认无误后合并

👍 团队协作推荐 ✔ 可审查 ✔ 可讨论 ✔ 可记录 ✔ 可回滚 ✔ 可保证质量

# 方式 B：本地手动合并（不推荐团队协作）

text 
git checkout dev
git pull origin dev
git merge 待合并的分支名
git push origin dev

适用于个人项目或紧急情况，团队合作优先使用 PR 流程

# 验证 dev 分支是否正常

业务分支合并到 dev 后，必须确保 dev 工作正常：

  • ⭐ 能否正常编译？
  • ⭐ 项目能否正常启动？
  • ⭐ 功能是否符合预期？
  • ⭐ 是否影响了其它同事的功能？
  • ⭐ 冲突是否正确解决？
  • ⭐ （如有）单元测试 / UI 测试是否通过？

只有 dev 完全验证通过后，才能进入下一步

# dev 分支 → main 分支（稳定版本）

当 dev 分支稳定后，可将其合并进 main

推荐同样使用：PR / MR （参考上文的方式 A）

本地方式如下：

text 
git checkout main
git pull
git merge dev
git push

main 分支代表最终上线版本，必须确保绝对稳定

# 删除业务分支

当业务分支已成功合并并验证无误，可以删除该分支：

# 删除本地分支

text 
git branch -d 分支名

# 删除远程分支

text 
git push origin --delete 分支名

分支删除后不影响历史记录，因为所有提交已归档在 main 和 dev 中

# 补充：业务分支在开发周期较长时需要定期与主干同步（关键）

当业务分支开发时间较长，而 dev 或 main 已经发生较大更新时，业务分支必须定期与主干同步，以避免最终合并时出现大量冲突
