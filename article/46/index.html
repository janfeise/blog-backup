从事件驱动到流程驱动：使用 Promise 组织前端业务流程

阅读时间约 35 分钟 · 字数 6943

文档：https://zgq.me/posts/react-app-dev/

promise文档：https://developer.mozilla.org/zh-CN/docs/Web/JavaScript/Reference/Global_Objects/Promise

最近看到了上述的一篇文档，作者提出Event based -> 命令式，从事件驱动到流程驱动，两者的区别在于：业务是否割裂

  • 事件驱动：业务可能存在割裂，一条完整流程，却被拆成了多个独立事件

  • 流程驱动：业务流程完整

下面以删除功能需弹窗二次确认举例，说明两者的区别

# 什么是事件驱动

事件驱动最大的特点是：

代码围绕事件组织，而不是围绕业务流程组织

例如，一个带二次确认的删除功能，其真实业务流程其实非常简单：

text 
点击删除
    ↓
用户确认
    ↓
删除数据

但在传统事件驱动模式下，它通常会被拆分为多个事件

业务流程：

text 
点击删除
    ↓
handleDelete()

——————————

用户点击确认
    ↓
handleConfirm()

——————————

删除数据

对应代码：

js 
const handleDelete = () => {
  setVisible(true);
};

const handleConfirm = async () => {
  await deleteApi();
  loadList();
};

可以发现，一个完整的业务流程被拆散到了两个不同的函数中

阅读代码时，需要开发者自己在脑海中拼接整个执行过程：

text 
handleDelete
    ↓
Modal
    ↓
handleConfirm
    ↓
deleteApi

当业务继续扩展，例如增加权限校验、日志记录、页面跳转、异常处理等步骤时，这种割裂会越来越明显，业务逻辑会分散到多个事件、多个回调甚至多个组件中，维护成本也随之增加

# 什么是流程驱动

流程驱动与事件驱动最大的区别在于：

代码按照业务执行顺序组织，而不是按照事件触发顺序组织

同样的删除功能，可以组织成下面这种形式：

业务流程：

text 
开始

↓

确认

↓

删除

↓

结束

对应代码：

js 
const deleteFlow = async () => {
  // 显示弹窗 
  await showConfirm();

  // 删除数据
  await deleteApi();

  // 其它流程
  await loadList();
};

阅读这段代码时，不需要再去寻找 handleConfirm() 在哪里，也不需要在脑海中拼接流程；代码的执行顺序，就是业务发生的顺序

随着流程越来越复杂，这种优势会越来越明显

# Promise：连接事件与流程的桥梁

那么，如何把事件驱动转换成流程驱动？“—— Promise

在 MDN 中，Promise 有一个示例：

js 
const myPromise = new Promise((resolve, reject) => {
  setTimeout(() => {
    resolve("foo");
  }, 300);
});

整个执行过程如下：

text 
创建 Promise
    ↓
Promise 进入 Pending（等待）
    ↓
300ms 后调用 resolve()
    ↓
Promise 完成（Fulfilled）

Promise 在等待 resolve() 或 reject() 被调用，上述例子中setTimeout 则在 300ms 后调用了 resolve()，结束 Promise

实际上，任何未来发生的事情都可以调用 resolve()，例如：

  • 网络请求完成
  • 文件上传完成
  • WebSocket 收到消息
  • 用户点击按钮

因此，对于 Modal 而言，我们也可以把"等待用户点击确认"包装成一个 Promise

# showConfirm 做了什么

在流程驱动版本中(下面有完整的<u>流程驱动代码</u>)，其中最关键的代码就是 showConfirm：

js 
// 保存 Promise 的回调
let resolveFn = null;
let rejectFn = null;

/**
 * 将 Modal 封装成 Promise
 */
function showConfirm(item) {
  // 显示弹窗，并记录待删除的数据
  deleteItem.value = item;
  modalVisible.value = true;

  // 返回 Promise，等待用户操作
  return new Promise((resolve, reject) => {
    resolveFn = resolve; // 保存 resolve 回调
    rejectFn = reject; // 保存 reject 回调
  });
}

关键在于需要把 resolve 和 reject 回调保存起来

因为：new Promise() 创建时可以拿到 resolve 和 reject，但是用户点击按钮发生在未来，只有将其保存下来后续才能调用

执行时间线如下：

text 
deleteFlow()

↓

showConfirm()

↓

创建 Promise

↓

保存 resolve / reject

↓

打开 Modal

↓

Promise 保持 Pending

↓

deleteFlow 暂停（await）

……

用户点击确认

↓

调用 resolve()

↓

Promise 完成

↓

deleteFlow 继续执行

因此，showConfirm 的真正作用并不是显示 Modal，而是：

创建一个 Promise，并把未来控制 Promise 状态的方法保存下来

# 用户点击确认后发生了什么

当用户点击"确定"按钮时：

js 
function confirmModal() {
  modalVisible.value = false;
  resolveFn?.();
}

调用 resolve() 后，Promise 状态发生变化：

text 
Pending
    ↓
resolve()
    ↓
Fulfilled

于是：

js 
await showConfirm();

立即结束等待，继续执行下面的代码：

js 
async function deleteFlow(item) {
  await showConfirm(item);

  list.value = list.value.filter(i => i !== item);

  console.log("删除成功");
}

如果用户点击取消：

js 
function cancelModal() {
  modalVisible.value = false;
  rejectFn?.();
}

则会调用 reject()

由于 await 抛出了异常，因此流程会直接进入：

js 
catch () {
  console.log("用户取消删除");
}

整个异常处理也变得十分自然

# 事件驱动完整代码

vue 
<template>
  <div>
    <li v-for="i in list" :key="i">
      <span>{{ i }}</span>
      <a-button danger @click="showModal(i)">删除</a-button>
    </li>

    <!-- 二次确认弹窗 -->
    <a-modal v-model:open="modalVisible" title="确认删除" @ok="handleOk">
      确定要删除 {{ deleteItem }} 吗？
    </a-modal>
  </div>
</template>

<script setup>
import { ref } from "vue";

const list = ref([1, 2, 3, 4, 5]);
const modalVisible = ref(false);
const deleteItem = ref(null);

const showModal = (item) => {
  deleteItem.value = item;
  modalVisible.value = true;
};

const handleOk = () => {
  if (deleteItem.value !== null) {
    list.value = list.value.filter((i) => i !== deleteItem.value);
    console.log("删除成功");
  }
  modalVisible.value = false;
};
</script>

# 流程驱动的完整代码

vue 
<template>
  <div>
    <li v-for="item in list" :key="item">
      <span>{{ item }}</span>
      <a-button danger @click="deleteFlow(item)"> 删除 </a-button>
    </li>

    <a-modal
      v-model:open="modalVisible"
      title="确认删除"
      @ok="confirmModal"
      @cancel="cancelModal"
    >
      确定要删除 {{ deleteItem }} 吗？
    </a-modal>
  </div>
</template>

<script setup>
import { ref } from "vue";

const list = ref([1, 2, 3, 4, 5]);

const modalVisible = ref(false);
const deleteItem = ref(null);

// 保存 Promise 的回调
let resolveFn = null;
let rejectFn = null;

/**
 * 将 Modal 封装成 Promise
 */
function showConfirm(item) {
  // 显示弹窗，并记录待删除的 item
  deleteItem.value = item;
  modalVisible.value = true;

  // 返回一个 Promise，等待用户操作
  return new Promise((resolve, reject) => {
    resolveFn = resolve; // 保存 resolve 回调
    rejectFn = reject; // 保存 reject 回调
  });
}

/**
 * 删除流程
 */
async function deleteFlow(item) {
  try {
    // 等待用户确认
    await showConfirm(item); // 弹窗点击确认后会结束promise，继续执行下面的逻辑

    // 删除数据：在开发时可替换为具体的接口请求
    list.value = list.value.filter((i) => i !== item);

    console.log("删除成功");
  } catch {
    // catch捕获的是：reject()，即用户取消删除
    console.log("用户取消删除");
  }
}

/**
 * 用户确认
 */
function confirmModal() {
  modalVisible.value = false;
  resolveFn?.(); // 调用 resolve，继续执行删除流程
}

/**
 * 用户取消
 */
function cancelModal() {
  modalVisible.value = false;
  rejectFn?.(); // 调用 reject，终止删除流程
}
</script>

# 原文: 事件驱动->Flow

# Event based -> 命令式

对于一些相对较长的 Flow，尽可能用命令式的写法去组织代码，可以让业务逻辑的表达更加直观清晰。但有时候涉及到类似 Modal 组件 visible，用户交互 confirm 后、再继续往下走的流程，代码上就很容易出现前面说到的业务逻辑跳来跳去的情况。

一个可以参考的做法是，把这种类似 Modal 交互的 Event based 逻辑转换为命令式的写法。代码层面可以用 Promise 构造函数 + Ref 的方式来实现，外层 Flow 直接 await 这个 Promise，当用户在 Modal 确认后，通过 resolve / reject 结束 Modal 的 Flow，再把流程交还给上层 Flow 继续往下走。

如以下例子代码，这里忽略了一些定义、传值的细节。在实际的操作上，你还可以把这类逻辑封装成一个 hook 实现通用化。

tsx 
const TestComponent = () => {
  const [modalVisible, setModalVisible] = useState<boolean>(false);
  const resolveRef = useRef(null);
  const rejectRef = useRef(null);

  const startModalFlow = () => new Promise((resolve, reject) => {
    resolveRef.current = resolve;
    rejectRef.current = reject;
    setModalVisible(true);
  });
  
  const startMainFlow = async () => {
    // before modal flow logic...
    await startModalFlow();
    // follow up logic...
  };

  return (
    <TestModal
      visible={modalVisible}
      onConfirm={() => {
        resolveRef.current?.();
        setModalVisible(false);
      }}
      onCancel={() => {
        rejectRef.current?.();
        setModalVisible(false);
      }}
      onClose={() => {
        rejectRef.current?.();
        setModalVisible(false);
      }}
  );
};

当我们能把业务流程用命令式的写法串起来以后，即使涉及到流程结束、报错的情况，我们也可以很轻松地兜住，正常结束我们可以用 return，异常结束可以直接 throw 一个定义好的 Exception / Error，只需要简单地用 try / catch 等语法就能实现错误的统一处理。并且，这样的做法也可以促使开发者多多思考业务的错误降级、兜底逻辑，对用户使用过程可能遇到的各种场景都有预期去做兜底，获得更加丝滑的体验。
