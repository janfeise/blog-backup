# 目的

用户行为数据采集的目的：<u>推荐</u>，为用户推荐相关内容

# 采集数据

需采集以下数据：

  • PV：Page View，页面浏览量，某个页面被打开了多少次
  • UV：Unique Visitor，有多少个用户访问
  • 停留时长：页面停留时长
  • 点击：用户点击量

# PV采集

分为两类：

  • MPA（传统页面）：死守 window.load，加载完就报
  • SPA（单页应用）：路由变了页面不刷新咋办？劫持 history.pushState 和 replaceState，再监听 popstate，路由一变，PV 立马 +1

注：SPA和MPA区别：

  • MPA (Multi-Page Application)：传统多页应用（如京东首页跳转详情页），每次跳转都会重新加载 HTML，触发 window.load
  • SPA (Single-Page Application)：现代单页应用（如 Vue/React 项目），页面跳转不刷新浏览器，只是 JS 换了内容，不会触发 window.load

# UV采集

localStorage存储用户来访信息

在浏览器本地 (localStorage) 盖个章。如果发现今天已经盖过章了，就不重复上报了

# 停留时长采集

  • 通用招数：监听 beforeunload（页面要关了）和 visibilitychange（页面隐藏了），一旦触发就计算时间。
  • SPA 特攻：路由切换时（pushState/popstate），除了报 PV，还得把上一页的停留时间给结清了。

# 逻辑

# 流程

存储校验（Storage）：初始化时，先检查 localStorage，判断是新客还是回头客（UV 校验）

核心采集（Collection）：启动监听器，分别捕获 PV、点击和停留时长

数据上报（Reporting）：所有数据最终汇聚到上报模块，发送给服务端

# 数据存储

由于前端没有“长期存储”功能，一旦用户刷新页面，在前端定义的数据就会刷新，恢复默认值，此时记录的用户数据会丢失，因此需考虑数据存储策略

  • localstorage等浏览器存储：有被篡改的风险

目前采用的方法是：将数据 + hash 值存储在localstorage，后端根据数据校验 hash 是否一致，若 hash 不匹配，后端可拒绝或修正

hash由：数据 + 时间戳 生成

js 
import CryptoJS from 'crypto-js'

const secretKey = 'my-secret-key'

// 保存数据
const dataStr = JSON.stringify(data)
const hash = CryptoJS.HmacSHA256(dataStr, secretKey).toString()
localStorage.setItem('behaviorData', JSON.stringify({ data, hash }))

// 上报时，后端可校验 hash 是否一致

存在的问题：前端的秘钥是完全暴露的，被获取后，hash值可以被篡改

# 数据生命周期管理

目前是将用户行为数据存储在 localstorage ，每次用户触发埋点时：继承 localstorage 已有的数据，然后进行更新，存在问题：

  • 数据无限累积，缺少时间维度的生命周期管理

在 初始化阶段做「用户行为数据生命周期校验」

  • 行为数据是“按天”的临时缓存，不是永久日志

# 数据上报时机

对于点击量收集，即用户点击了哪些内容，此时可考虑以下上报时机：

  • 页面刷新上报

  • 定时上报 【通用】

  • 用户离开网站时上报【通用】

注：不同类型的用户行为数据，上报时机不同，通用的是：定时上报 + 用户离开网站时上报

# 前端发送请求方式抉择

# 1. axios / fetch

axios / fetch 常用于日常接口中，但是在用户行为数据采集业务中：由于 页面刷新/关闭时异步请求可能失败，因此不可用于 页面 卸载时发送请求

适合的上报时机：

  • 定时上报

# 2. navigator.sendBeacon

navigator.sendBeacon 特性：

  • 不会阻塞页面关闭
  • 无法带自定义请求头（如 token）
  • 不关心响应结果

因此 navigator.sendBeacon 适合的上报时机：

  • 页面刷新

  • 页面卸载

js 
try {
    const payload = new Blob([JSON.stringify(data)], { type: 'application/json' })
    if (navigator.sendBeacon) {
        navigator.sendBeacon(url, payload)
    }
} catch (beaconError) {
    console.warn('sendBeacon降级方案也失败:', beaconError)
}

# 总结

  • 页面刷新采用：navigator.sendBeacon
  • 定时上报采用：axios / fetch
  • 页面卸载采用：navigator.sendBeacon

由于：页面卸载使用 navigator.sendBeacon 发送数据，而 navigator.sendBeacon 无法携带 token，因此存在问题：

  • 登录的用户无法绑定数据：由于无法携带 token ，无法绑定用户

解决方法：初次进入网站时，使用 axios / fetch 发送数据

由于用户卸载了页面，在下次进入网站时，如果用户是登录状态：使用 axios / fetch 发送数据

# 数据库：用户行为数据表设计

# 表设计目标

  • 统计用户不同时间段的行为数据（在不同时间段推荐不同的数据）
  • 时间可分析：按天/月/年统计用户行为
  • 全量记录：登录/匿名用户、不同类型行为、不同目标

下面以“程序猿”项目的用户行为表设计为示例：

sql 
CREATE TABLE user_behavior (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  
  user_id BIGINT NULL COMMENT '登录用户ID',
  anonymous_id VARCHAR(64) NULL COMMENT '未登录用户匿名ID',
  
  behavior_type VARCHAR(32) NOT NULL COMMENT '行为类型：problem_click/post_click/tag_click',
  target_id BIGINT NOT NULL COMMENT '目标ID：题目/帖子/标签',
  click_count INT DEFAULT 1 COMMENT '点击总数',
  
  data_hash VARCHAR(256) NULL COMMENT '数据完整性哈希',
  
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  
  year INT GENERATED ALWAYS AS (YEAR(created_at)) STORED COMMENT '创建年份',
  month INT GENERATED ALWAYS AS (MONTH(created_at)) STORED COMMENT '创建月份',
  day INT GENERATED ALWAYS AS (DAY(created_at)) STORED COMMENT '创建日期',
  
  -- 索引
  INDEX idx_behavior_type (behavior_type),
  INDEX idx_created_at (created_at),
  INDEX idx_year_month_day (year, month, day)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

# 系统推荐

基于全局行为数据和业务规则的非个性化推荐方式，常用于广场、榜单等场景。它通过对用户行为数据进行聚合统计，计算内容热度并排序展示，是个性推荐的重要兜底方案

# 业务场景

在“程序猿”项目中，由于系统不强制登录，此时未登录也能访问系统，此时存在两种情况：

  • 未登录用户数据采集
  • 已登录用户数据采集

存在问题：未登录用户后续登录后应该如何处理？——数据迁移

通过 anonymousId 关联用户，若用户后续登录后，将 anonymousId 的数据迁移至 userId

# 用户状态变化场景分析

背景

  • 系统 不强制登录
  • anonymousId 由前端生成并存储在 localStorage
  • localStorage 中的用户行为数据 不会因登录/退出登录自动清空
  • 登录态由是否携带 token 决定

# 场景 1：始终登录状态（理论存在，实践中可忽略）

⚠️ 说明：从系统生命周期角度看，该场景几乎不存在

# 原因说明
  • 用户第一次访问系统时一定是未登录状态
  • 前端初始化阶段必然会生成并保存 anonymousId
  • 即使用户随后立即登录，anonymousId 依然存在于 localStorage
# 结论

➡ “anonymousId 为空 + 始终登录”在真实业务中几乎不会出现

因此该场景在设计中可不单独处理

# 场景 2：始终未登录状态

# 状态特征
  • 请求 不携带 token
  • localStorage 中 存在 anonymousId
# 行为数据处理
  • 所有用户行为数据：
    • 仅使用 anonymousId 作为唯一标识
    • 不关联 userId
  • 数据可直接入库或先本地缓存后再上报

✔ 该场景逻辑简单，无需特殊处理

# 场景 3：未登录 → 登录（核心场景 ⭐）

# 状态特征
  • 登录成功后：
    • 请求开始携带 token
    • localStorage 中 仍然存在 anonymousId
      • 因为匿名行为数据不能被覆盖或删除
  • 因此出现 双身份并存 状态：
    • userId（登录态）
    • anonymousId（历史行为标识）
# 问题本质

如果不处理，会导致：

  • 用户<u>历史行为</u> 无法计入登录用户画像
  • 推荐系统、行为分析出现数据割裂
# 处理方式（关键逻辑）
  1. 用户登录成功
  2. 前端请求同时携带：
    • token
    • anonymousId
  3. 后端执行数据迁移逻辑：
    • 将 anonymousId 对应的历史行为数据
    • 批量更新关联到 userId
  4. 迁移完成后：
    • 后续行为数据 只以 userId 作为标识
    • anonymousId：
      • 可保留（推荐，用于异常兜底）
      • 或标记为已迁移 / 废弃

✅ 目标 保证用户行为数据在“未登录 → 登录”过程中的 连续性、一致性与可追溯性

# 场景 4：登录 → 未登录（退出登录）

# 状态分析
  • 用户第一次进入系统：
    • 未登录
    • 已生成 anonymousId
  • 登录后：
    • anonymousId 未被删除（退出登录后，系统没有对 anonymousid 进行删除）
  • 退出登录后：
    • token 被清除
    • anonymousId 依然存在于 localStorage
# 行为数据处理
  • 退出登录后的用户行为：
    • 继续使用现有 anonymousId 进行采集
    • 行为数据重新以匿名用户身份入库
  • 不需要额外迁移操作

✔ 该行为符合用户真实使用路径

# 特殊情况：用户主动清除本地数据

# 情况说明
  • 用户手动删除：
    • localStorage
    • 浏览器缓存
    • 或使用无痕模式
# 系统处理策略
  • 前端检测到 anonymousId 不存在
  • 自动重新生成新的 anonymousId
  • 该逻辑 与是否登录无关

📌 影响说明：

  • 行为数据会被视为 新匿名用户
  • 属于可接受的数据自然丢失场景

# 系统推荐：帖子推荐设计

  • 属于系统推荐

背景：在“程序猿”广场页面，根据 帖子数据 和 用户行为数据，实时推荐热门帖子

  1. 原始数据帖子表评分设计：

    text 
    base_score =
  view_count    * 1
+ like_count    * 3
+ comment_count * 4

    原因：

    • view：低成本行为
    • like：明确正反馈
    • comment：强互动

  2. 用户行为数据表

    text 
    behavior_score = total_click * 1.5

    由于在该项目中：用户行为数据记录的是——最新时间下用户行为数据的采集，相较于帖子数据，时间更新，占比权重大于：view_count

  3. 时间衰减：从创建日期开始衰减，采用 非线性单调递减的幂律函数 (Power-law Decay)。随着创建时间增长，内容权重呈非线性下降，平衡新旧数据的影响力 $$ time_decay = \frac{1}{(days_since_create + 1)^{0.5}} $$

    特点：

    • 新帖优势明显
    • 老帖不会瞬间归零

    创建时间 间隔天数 (x) 返回值 (timeDecay) 权重剩余
    今天 0 $1 / \sqrt{1} = 1.0$ 100%
    3天前 3 $1 / \sqrt{4} = 0.5$ 50%
    8天前 8 $1 / \sqrt{9} = 0.33$ 33%
    24天前 24 $1 / \sqrt{25} = 0.2$ 20%
    99天前（三个月前的帖子） 99 $1 / \sqrt{100} = 0.1$ 10%

# 总结：最终帖子热度评分计算

热度计算应将静态累计指标与动态用户行为拆分处理：view_count / like_count / comment_count 属于历史认可度，天然会累积增长，必须结合帖子创建时间做时间衰减以避免老帖长期霸榜；而用户行为采集的 post_click 是实时、高频、强时效数据，应仅统计最近 7 天，并在行为层面做轻量时间衰减或直接作为动态分使用，不应再参与整体时间衰减。因此，合理的热度模型应为：静态分 × 静态时间衰减 + 近 7 天行为动态分（可加权），这样才能同时反映“长期价值”和“当前热度” $$ hot_score=(view_count∗1+like_count∗3+comment_count∗4)×time_decay

  • total_click_7d∗1.5 $$

# 定时更新

不必每次实时计算，推荐：

  • 定时任务（5～10 分钟）

  • 计算 hot_score

  • 写入redis post_hot_stat

# 触发事件

  1. 帖子删除：当帖子删除时应该重新计算帖子热度，因为可能删除的帖子是：热度帖子，此时帖子被删除，无法查看，因此需要情况redis缓存重新计算热度
  2. 帖子发布无需更新缓存，无需重新计算帖子热度：因为刚发布的帖子不可能登上热度榜，况且缓存时间设置为5分钟，5分钟后重新计算

# 个性化推荐：热门题目

由于题目关联了标签：因此可以通过计算用户感兴趣的标签为用户推荐相关题目

用户个性化推荐通过用户行为数据（题目点击、标签点击、题目收藏）映射至<u>标签维</u>度，计算用户对各标签的兴趣强度。其中题目点击与标签点击为即时兴趣信号，而<u>收藏行为</u>作为强兴趣信号需引入<u>时间衰减函数</u>。最终基于高热度兴趣标签，从关联题目中筛选并排序推荐内容。

标签热度计算：

基于用户最近一次收集的用户行为数据开始，向前回溯的7天，计算这7天内的行为数据 $$ tag_score = 题目点击次数对应的标签 * 1

  • 标签点击次数 * 0.5
  • 收藏题目对应的标签 * 3 * time_decay $$
  1. 题目点击 & 收藏题目 ⇒ 必须映射到标签
  2. 时间衰减用于收藏行为，收藏是长期兴趣，但会“过时”
  3. 点击、标签点击本身已经是“短期行为”，可以不加衰减
  4. 需识别用户身份，通过用户身份进行题目的标签热度计算（与系统推荐不同，系统推荐无需关注用户身份，直接全部统计，但是个性化推荐不同，需根据用户的身份进行筛选，不能全部统计）

注意：冷启动，若用户未登录、无点击、无收藏，此时需有兜底策略

# 数据存储

  • 个性化导致存储量过大，无法直接缓存每个用户的完整推荐列表，如果需要存储，由于是个性化推荐，那么每个用户都需要存储热门题目数据，导致：用户数 × 推荐条数 → 数据量大

解决方法：

折中存储：只存储每个用户的兴趣标签，不存储题目数据，其中兴趣标签只存放两个字段：标签id和评分，类型为 Set，按照 score 排序（降序），再从标签中返回题目列表

# 匿名用户和登录用户

匿名用户：根据用户行为数据采集的进行推荐，由于未登录并没有收藏数据
