前端 DocumentFragment 使用分析

阅读时间约 32 分钟 · 字数 6384

文档：https://developer.mozilla.org/zh-CN/docs/Web/API/DocumentFragment

背景：在项目obsidian-to-memo中，每条message都是直接插入dom元素的，n条消息便设计n次dom更新，在chatGpt的回答中，提到了一个更好的解决方案：DocumentFragment

在前端开发中，DOM 操作一直都是性能优化的重要部分。尤其是在批量渲染列表、动态生成大量节点时，不合理的 DOM 更新方式很容易导致页面卡顿。

而 DocumentFragment，正是浏览器提供的一种专门用于优化 DOM 批量操作的机制。

# 什么是 DocumentFragment？

DocumentFragment 是一种轻量级的 DOM 容器。

它本身不属于真实页面 DOM 树的一部分，可以理解为：

  • 一个“临时容器”：临时存放多个dom元素，将多个dom元素一次渲染，而非每个dom元素都触发一次渲染
  • 一个“临时仓库”
  • 一个“离线 DOM”
  • 一个“虚拟容器”

它允许开发者先在内存中构建一批 DOM 节点，最后一次性插入页面（插入只有一次）。

js 
const fragment = new DocumentFragment()

或者：

js 
const fragment = document.createDocumentFragment()

二者效果相同。

# DocumentFragment 的核心特点

# 不在真实 DOM 树中

这是最关键的一点。

因为它不在页面文档流中：

  • 不会触发页面重排（Reflow）
  • 不会触发页面重绘（Repaint）
  • 不会影响当前页面布局

所有节点操作都发生在内存中。

# 它的出现是为了解决什么问题？

核心目标：

减少频繁 DOM 操作带来的性能消耗

# 为什么频繁操作 DOM 性能差？

因为 DOM 并不仅仅是一个 JavaScript 对象。

DOM 与：

  • 浏览器渲染引擎
  • Layout
  • Paint
  • Composite

都有关系。

每次向页面插入元素：

js 
list.appendChild(li)

浏览器都可能需要：

  1. 更新 DOM 树
  2. 重新计算布局
  3. 更新渲染树
  4. 进行重绘

如果循环中不断操作：

js 
for (...) {
  list.appendChild(li)
}

就可能触发大量渲染计算。

# DocumentFragment 的优化思路

传统方式：

txt 
创建一个元素
↓
插入 DOM
↓
浏览器更新页面
↓
再创建一个元素
↓
再插入 DOM
……

频繁的dom插入

而 DocumentFragment：

txt 
先在内存中批量创建
↓
统一插入页面
↓
浏览器只更新一次

这也是它最大的价值。

# 示例分析

代码如下：

js 
const list = document.querySelector("#list");
const fruits = ["Apple", "Orange", "Banana", "Melon"];

const fragment = new DocumentFragment();

fruits.forEach((fruit) => {
  const li = document.createElement("li");
  li.textContent = fruit;
  fragment.appendChild(li);
});

list.appendChild(fragment);

# 执行流程分析

# 第一步：创建 fragment

js 
const fragment = new DocumentFragment();

此时：

txt 
fragment
└── (空)

它还未进入页面 DOM。

# 第二步：创建 li 元素

js 
const li = document.createElement("li");

生成节点：

txt 
<li></li>

# 第三步：写入文本

js 
li.textContent = fruit;

变成：

txt 
<li>Apple</li>

# 第四步：放入 fragment

js 
fragment.appendChild(li);

注意：

这里并没有进入页面。

只是进入：

txt 
fragment
├── <li>Apple</li>
├── <li>Orange</li>
├── <li>Banana</li>
└── <li>Melon</li>

所有操作都在内存中完成。

# 第五步：统一插入页面

js 
list.appendChild(fragment);

浏览器会：

  • 将 fragment 中所有子节点移动到 list
  • fragment 自动清空
  • 页面只进行一次真实 DOM 更新

最终：

txt 
<ul id="list">
  <li>Apple</li>
  <li>Orange</li>
  <li>Banana</li>
  <li>Melon</li>
</ul>

# appendChild 后会“清空自身”

这是容易忽略的地方:

js 
list.appendChild(fragment)

执行后：

  • fragment 内的所有子节点会移动到 list
  • fragment 自身会变为空

类似于：

txt 
fragment -> 搬运车
DOM -> 最终目的地

它更像是一个“临时容器”，临时存放多个dom，到达目的地后批量卸载，只触发一次DOM更新。

# 直接创建 DOM 和 Fragment 创建的区别

# 方式一：直接插入 DOM

js 
fruits.forEach((fruit) => {
  const li = document.createElement("li");
  li.textContent = fruit;

  list.appendChild(li);
});

执行过程：

txt 
创建
↓
插入 DOM
↓
浏览器更新

创建
↓
插入 DOM
↓
浏览器更新

如果数据量很大：

txt 
1000 次 appendChild
=
1000 次 DOM 更新机会

性能开销较大。

# 方式二：使用 DocumentFragment

js 
const fragment = new DocumentFragment();

fruits.forEach((fruit) => {
  const li = document.createElement("li");
  li.textContent = fruit;

  fragment.appendChild(li);
});

list.appendChild(fragment);

执行过程：

txt 
内存中批量创建
↓
统一 append
↓
只更新一次页面

性能明显更稳定。

# 性能差异的本质

很多人误以为：

createElement 很慢

实际上：

真正昂贵的是：

txt 
DOM Tree 更新
+
Layout 计算
+
Paint

而不是：

js 
document.createElement()

DocumentFragment 优化的不是“创建元素”。

而是：

减少真实 DOM 插入次数

# Fragment 一定更快吗？

不一定。

这是一个常见误区。

# 小数据量时差距很小

例如：

js 
4 个 li

现代浏览器优化已经非常强。

性能差异可能几乎测不出来。

# 大量 DOM 时优势明显

例如：

txt 
1000+
5000+
10000+

批量渲染时：

  • Fragment
  • innerHTML
  • 虚拟 DOM

优势会逐渐明显。

# Fragment 与 innerHTML 的区别

很多时候：

js 
list.innerHTML = html

甚至可能更快。

因为浏览器底层会直接解析 HTML 字符串。

# Fragment 的优势在于

# 更安全

不会拼接 HTML 字符串。

避免：

txt 
XSS

风险。

# 更适合复杂节点逻辑

例如：

  • 事件绑定
  • 条件渲染
  • 动态组件
  • 嵌套节点

# 更符合组件化思维

现代框架本质上都在做类似事情：

txt 
先在内存构建
↓
再统一提交更新

例如：

  • React Fiber
  • Vue Virtual DOM

思想其实与 Fragment 很接近。

# 现代框架中为什么很少手动使用 Fragment？

因为：

React/Vue 已经帮开发者做了。

例如 React：

txt 
JSX
↓
Virtual DOM
↓
Diff
↓
批量更新真实 DOM

本质上已经具备：

txt 
离线构建
统一提交

能力。

所以：

  • 原生 DOM 开发中很有价值
  • 框架开发中感知较弱

# 批量列表渲染

# 聊天消息加载

例如：

txt 
聊天窗口
日志系统
消息流

# 表格大量渲染

txt

# 虚拟滚动预渲染

例如：

txt

# 一个更直观的性能对比

# 普通方式

js 
for (let i = 0; i < 10000; i++) {
  const div = document.createElement("div");
  list.appendChild(div);
}

特点：

txt 
频繁真实 DOM 操作

# Fragment 方式

js 
const fragment = new DocumentFragment();

for (let i = 0; i < 10000; i++) {
  const div = document.createElement("div");

}

list.appendChild(fragment);

特点：

txt 
只进行一次真实插入

# 总结

DocumentFragment 的核心思想非常简单：

先在内存中批量构建 DOM，再一次性插入页面

它优化的重点并不是：

txt 
createElement

而是：

txt 
减少真实 DOM 更新次数

在：

  • 大量列表渲染
  • 高频消息更新
  • 批量节点插入

场景下，它能有效减少：

txt 
Reflow
Repaint

带来的性能损耗。

虽然现代框架已经帮我们屏蔽了很多底层细节，但理解 DocumentFragment 仍然非常重要。

因为它本质上反映的是：

前端渲染性能优化的底层思想：减少真实 DOM 的频繁变更

# 疑问

疑问：也就是说，相较于逐次渲染每个dom元素如：<ul>、<li>……<li>，一次渲染整个dom元素，如：<ul><li><li><li>……</ul>的开销更小？

回答：是的

一次性把完整 DOM 结构提交给浏览器，通常比“边创建边插入”更高效

因为浏览器真正昂贵的部分不是：

text 
document.createElement()

而是：每次dom更新都会触发

text 
DOM Tree 更新
Layout（回流）
Paint（重绘）

使用documentFragment浏览器只需要触发：

text 
一次 DOM 更新
一次布局
一次绘制

直接操作DOM，就像你买5支雪糕，却买一支（dom 更新）就跑回家一趟（dom 布局计算和绘制），如此反复5次。而使用DocumentFragment，相当于一口气买齐5支，一次带回家，时间自然更短，性能也更好。
