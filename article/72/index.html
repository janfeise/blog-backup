# 从后端一段SQL代码到MySQL的执行流程

客户端发送SQL查询语句到MySQL服务器，MySQL处理请求，并与客户端建立连接，获取权限，后续MySQL的解析器对SQL语句进行解析，检查是否符合SQL语法规则，通过后优化器尝试找出最高效的方式来执行查询，执行器调用存储引擎的API进行数据的读写，并返回给客户端完成本次查询

第一步，客户端发送 SQL 查询语句到 MySQL 服务器。

第二步，MySQL 服务器的连接器开始处理这个请求，跟客户端建立连接、获取权限、管理连接。

第三步，解析器开始对 SQL 语句进行解析，检查语句是否符合 SQL 语法规则，确保引用的数据库、表和列都存在，并处理 SQL 语句中的名称解析和权限验证。

第四步，优化器负责确定 SQL 语句的执行计划，这包括选择使用哪些索引，以及决定表之间的连接顺序等。优化器会尝试找出最高效的方式来执行查询。

第五步，执行器会调用存储引擎的 API 来进行数据的读写。

第六步，MySQL 的存储引擎是插件式的，不同的存储引擎在细节上面有很大不同。例如，InnoDB 是支持事务的，而 MyISAM 是不支持的。之后，会将执行结果返回给客户端

第七步，客户端接收到查询结果，完成这次查询请求。

Error Log 看 MySQL 自己出了什么问题；Binlog 看数据发生了什么变化；General Log 看客户端执行了什么 SQL；Slow Log 看哪些 SQL 执行得太慢

错误日志 Error Log 记录 MySQL 在启动、运行、停止过程中产生的错误、警告以及部分重要运行信息 默认开启 故障排查、定位 MySQL 启动失败或运行异常 例如数据库启动失败、存储引擎异常、权限问题等。错误日志本身并不是用于恢复业务数据的日志
二进制日志 Binary Log / Binlog 记录数据库中会导致数据或结构发生变化的事件，例如 CREATE、INSERT、UPDATE、DELETE 等；通常不记录普通 SELECT 查询 MySQL 8.0 默认开启 数据恢复、主从复制、数据同步 Binlog 主要有 STATEMENT、ROW、MIXED 三种格式。STATEMENT 记录执行的 SQL；ROW 记录行数据发生的变化；MIXED 根据情况在两者之间选择
通用查询日志 General Query Log 记录客户端连接以及 MySQL 接收到的各种 SQL 请求，包括 SELECT、INSERT、UPDATE、DELETE 等 默认关闭 排查 SQL 请求、分析客户端执行了哪些操作 记录范围非常广，写入频繁，性能开销较大，通常只在排查问题时临时开启
慢查询日志 Slow Query Log 记录执行时间超过指定阈值的 SQL 默认关闭 定位慢 SQL、进行数据库性能优化 通过 long_query_time 设置慢查询时间阈值，例如设置为 2，表示执行时间超过 2 秒的 SQL 可被记录

# innodb 存储引擎中 redolog 与 undolog 的区别

  • undolog：记录旧数据，即更新前的数据，用于回滚和MVCC多版本并发控制
  • redolog：记录修改，用于崩溃后恢复，由于innodb对于数据更改，缓冲区与实际存储数据的磁盘处理顺序不同，首先将位于内存的缓冲区数据更新，并写入redolog，若数据写入实际存储的磁盘时发生崩溃，此时重启后可以通过redolog重新恢复已提交的数据

redolog是MySQL存储引擎层innodb的日志记录文件，而binlog是MySQL server层的日志记录文件，redolog与innodb绑定，记录物理级别的修改操作，如：具体的索引、页、以及数据等内容，而binlog主要是逻辑层面的修改操作，有三种记录方式：statement、row、mixed（两者混合），其中statement记录SQL语句，row记录更改前后的数据

# MySQL 两阶段提交

背景：一条SQL语句进行更新操作设计了两阶段提交

  1. 为什么需要两阶段提交？
  2. 两阶段提交的流程是什么？

两阶段提交是为了保证 redolog 和 binlog 的一致性，由于 redolog 是 innodb 存储引擎的日志记录，而 binlog 是MySQL server层的日志记录，主要用于主从复制和数据恢复。如果两者独立提交，宕机时可能出现 redolog 有记录但 binlog 没有，或者 binlog 有记录但 redolog 没有，从而导致主库恢复结果与 binlog 不一致，因此 MySQL 将 redolog 的提交分为 prepare 与 commit 两个阶段，中间写入 binlog，以保证两套日志对同一个事务的提交状态保持一致

两阶段提交的流程是， innodb 先写 redolog，并将其标记为 prepare 状态，然后server 层写人binlog，binlog 写入成功后，再将 redolog 标记为 commit，事务完成；若后续发生故障可能进行回滚或者判断事务已经成功

如果在 prepare 后，binlog 前宕机，此时binlog没有成功写入，事务会回滚；如果 binlog 已经写入成功，但 redolog 仍处于 prepare 状态，重启后会根据 binlog 判断事务已经成功，并完成提交

其中真正的“两阶段”主要指 redo log 的：

text 
prepare
↓
commit

binlog 写入发生在这两个阶段之间

文本：“中华人民共和国”

  • ngram 分词结果：中华、华人、人民、民共、共和、和国

在高亮方面，由于对文本进行了分词，若后端进行高亮需知道分词的结果，然后才能进行高亮，而 ES 则支持高亮，无需后端处理，但MySQL只能返回全文搜索的结果与评分，高亮需后端进行处理

# MySQL 底层 B+树

MySQL 的数据最终存储在磁盘中，如果每次查询都直接扫描磁盘中的所有数据，查询效率会非常低

以 InnoDB 为例，它主要使用 B+ 树作为索引的数据结构，通过 B+ 树减少磁盘 I/O 次数，提高数据查询效率

需要注意：

  • InnoDB 的索引通常采用 B+ 树
  • 主键索引又称聚簇索引，叶子节点存储完整的行数据
  • 非叶子节点主要存储 索引键 + 子页指针
  • InnoDB 默认一个数据页大小为 16KB
  • B+树顶层存放于内存中，无需经过磁盘IIO，进一步减少了磁盘IO访问次数
# B+ 树如何存储数据

假设表中存在一个主键 id：

sql 
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(20),
    age INT
);

随着数据不断插入，InnoDB 会按照主键顺序组织聚簇索引

例如：

text 
1  2  3  4  5  6  7  8 ...

但 InnoDB 并不是直接将每条数据作为一个独立的 B+ 树节点，而是将多条记录存放在一个 数据页 Page 中

一个数据页默认大小为：

text 
16KB

因此整体结构可以简化理解为：

text 
                非叶子节点
              [100] [200] [300]
                ↓     ↓     ↓
             Page1  Page2  Page3
               ↓      ↓      ↓
             行数据   行数据   行数据

B+ 树的所有完整行数据都存储在叶子节点的数据页中，而非叶子节点只保存索引键以及指向下一层页面的指针

同时，叶子节点之间通过双向链表连接：

text 
Page1 ⇄ Page2 ⇄ Page3 ⇄ Page4

这样不仅可以快速进行单条数据查询，也非常适合范围查询

例如：

sql 
SELECT *
FROM user
WHERE id BETWEEN 100 AND 200;

MySQL 可以先通过 B+ 树找到 id = 100 所在的数据页，然后沿着叶子节点的链表继续向后扫描，而不需要重新从根节点查找每一条数据

核心原因是 B+ 树的扇出非常大，一个 16KB 的非叶子节点并不存储完整行数据，而主要保存：

text 
索引键 + 子页指针

因此一个索引页可以指向大量下一层页面，例如按照前面的简化模型：

text 
一个非叶子节点
≈ 可以指向 1365 个子节点

B+ 树每增加一层，理论容量都会成百上千倍增长，所以实际数据库中，即使存在几百万、几千万甚至更多的数据，B+ 树通常仍然只有较少的层数

↓

↓

因此 B+ 树能够使用很少的磁盘 I/O 完成大量数据中的定位

# 面试回答

InnoDB 的索引主要采用 B+ 树结构，一个数据页默认大小为 16KB

对于主键索引，也就是聚簇索引，完整的行数据存储在 B+ 树的叶子节点中，非叶子节点主要保存索引和指向下一层数据页的指针

因为非叶子节点不需要保存完整行数据，所以一个 16KB 的页面可以保存大量索引项

假设一个非叶子页大约可以指向 1000 多个子页，一个叶子页可以保存几百条数据，那么三层 B+ 树理论上就可以管理上亿条数据

同时叶子节点之间通过双向链表连接，因此 B+ 树不仅适合等值查询，也非常适合范围查询

# 聚簇索引与非聚簇索引

在 InnoDB 中，索引主要可以分为 聚簇索引（Clustered Index） 和 辅助索引（Secondary Index）。

# 聚簇索引

聚簇索引的特点是：索引和完整行数据存储在一起，如：主键索引，其 B+ 树的叶子节点存储完整的行数据。

例如：

sql 
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(20),
    age INT
);

主键索引可以简化理解为：

text 
                主键索引 B+ 树

                    目录
                 /       \
                /         \
             数据页       数据页

        id=1            id=10
        name=Tom        name=Jack
        age=20          age=25

叶子节点中不仅存在主键 id，还保存这一行的完整数据：

text 
id + name + age + ...

因此：

sql 
SELECT *
FROM user
WHERE id = 10;

通过主键索引找到对应的叶子节点后，就可以直接取得完整的数据。

InnoDB 一张表只能有一个聚簇索引，因为完整的行数据只能按照一种 B+ 树结构进行组织。

如果表中没有显式定义主键，InnoDB 会按照一定规则选择其他字段作为聚簇索引；如果仍然没有合适的字段，则会生成隐藏的行 ID 来组织数据。

# 非聚簇索引

InnoDB 中通常称为 辅助索引或二级索引（Secondary Index）。

例如为 name 创建索引：

sql 
CREATE INDEX idx_name
ON user(name);

此时会额外创建一棵以 name 为索引键的 B+ 树。

但辅助索引的叶子节点不会再次保存完整行数据，而是主要保存：

text 
辅助索引列 + 主键值

例如：

text 
name        id

Alice       5
Jack        10
Tom         1

因此可以简化理解为：

text 
辅助索引 B+ 树

          name
            ↓
        找到 Jack
            ↓
         得到 id=10

然后再通过：

text 
id = 10

去主键索引 B+ 树中查找完整行数据：

text 
辅助索引 B+ 树
      ↓
得到主键 id
      ↓
主键索引 B+ 树
      ↓
获得完整行数据

这种根据辅助索引取得主键值，再根据主键值查询聚簇索引的过程称为：

text 
回表

例如：

sql 
SELECT *
FROM user
WHERE name = 'Jack';

如果 name 上存在辅助索引，查询过程可以简化为：

text 
idx_name B+ 树
↓
找到 name = Jack
↓
取得主键 id = 10
↓
主键索引 B+ 树
↓
找到 id = 10
↓
获得完整行数据

也就是说，通常需要经过两棵 B+ 树。

不过，并不是所有辅助索引查询都一定需要回表。

例如：

sql 
SELECT id, name
FROM user
WHERE name = 'Jack';

假设存在：

sql 
INDEX idx_name(name)

辅助索引叶子节点本身已经保存：

text 
name + id

查询需要的字段都可以直接从索引中取得，因此无需再次查询主键索引。

# 面试回答

InnoDB 中主要有聚簇索引和非聚簇索引

聚簇索引，存放索引与数据，如：主键索引；而非聚簇索引，则主要存放非聚簇索引列和对应的主键值。

因此通过非聚簇索引查询完整数据时，通常先查询非聚簇索引的 B+ 树得到主键，再根据主键查询聚簇索引。如果查询需要的字段都已经包含在辅助索引中，则可以通过覆盖索引避免回表。

辅助索引之所以存储主键，而不是直接保存数据的物理地址，是因为 InnoDB 中数据页可能由于插入、删除、页分裂等操作发生位置变化，而主键作为逻辑标识更加稳定，可以降低多个辅助索引的维护成本。

常见的索引无法有效使用的情况包括：LIKE 以通配符开头、复合索引不满足最左前缀原则、OR 中存在无法使用索引的条件

# 面试回答

事务是一组要么全部成功、要么全部失败的数据库操作，具有 ACID 四个特性，分别是原子性、一致性、隔离性和持久性。

由于数据库中多个事务会并发执行，所以存在脏读、不可重复读和幻读等问题，因此数据库提供了 Read Uncommitted、Read Committed、Repeatable Read 和 Serializable 四种隔离级别，InnoDB 默认使用 Repeatable Read。

InnoDB 中 Read Committed 和 Repeatable Read 主要通过 MVCC 实现。MVCC 的核心由 Undo Log 版本链、记录中的事务信息以及 Read View 组成。数据发生修改后，旧版本通过 Undo Log 保存并形成版本链，事务进行快照读时通过 Read View 判断哪个版本对当前事务可见。

Read Committed 通常每次快照读都会创建新的 Read View，因此可能读取到其他事务最新提交的数据，产生不可重复读；Repeatable Read 通常在第一次快照读时创建 Read View，后续继续复用，因此可以保证同一个事务中的多次快照读看到相对一致的数据。

MVCC 允许不同事务读取同一条数据的不同版本，减少了读写之间的锁竞争，因此相比所有读取都依赖加锁，能够提供更高的并发性能。

不过 MVCC 主要解决快照读的问题，对于 UPDATE、DELETE、SELECT FOR UPDATE 等当前读操作，InnoDB 仍然需要结合行锁、间隙锁和 Next-Key Lock 等机制保证事务隔离。

# innodb为什么需要间隙锁、临界锁

背景：通过主键进行精确查询时，此时innodb会自动添加记录锁（行锁），如果是范围查询直接为该范围内的所有数据添加记录锁不就行了吗？为什么还细分为间隙锁、临界锁？

30

这就是典型的幻读，因此：

记录锁无法锁住“尚不存在的数据”

这就是间隙锁存在的根本原因

InnoDB 默认事务隔离级别为 可重复读（Repeatable Read，RR），在 RR 隔离级别下，InnoDB 主要通过两套机制处理幻读：

↓

当前读
↓

↓

InnoDB 在 RR 隔离级别下通过 MVCC 和锁机制共同解决幻读问题

# MVCC 与 Read View

MVCC 的核心基础包括：

text 
undo log 版本链
+
Read View 版本可见性规则

其中：

  • undo log 保存数据修改前的旧版本，并形成版本链
  • Read View 用于判断版本链中的哪些版本对当前事务可见

例如一条记录可能存在：

text 
最新版本 V3
    ↓
旧版本 V2
    ↓
旧版本 V1

事务读取数据时，并不是直接读取某份提前复制好的“数据快照”，而是：

text 
读取当前记录
↓
根据 Read View 判断当前版本是否可见
↓
如果不可见，则沿 undo log 版本链继续查找
↓
找到符合可见性规则的版本
↓
读取该版本对应的数据

因此更准确地说：

text 
Read View ≠ 数据快照
Read View = 版本可见性规则

可以把 MVCC 理解为：

数据可以产生多个版本，Read View 决定当前事务应该读取哪个版本

# READ COMMITTED 与 REPEATABLE READ

两种隔离级别的重要区别之一，是 Read View 的使用方式不同：

隔离级别 Read View 效果
READ COMMITTED 每次一致性快照读通常重新创建 可以看到其他事务最新已提交版本
REPEATABLE READ 一个事务中的一致性快照读通常复用第一次建立的 Read View 多次读取遵循相同的版本可见性规则

需要注意：

RR 并不是“相同 SQL 才复用 Read View”

而是：

同一个事务中的一致性快照读通常复用同一个 Read View

例如：

SQL 
SELECT * FROM user;
SELECT * FROM product;
SELECT * FROM orders;

虽然 SQL 不同，但都可以使用同一套版本可见性规则

间隙锁 保护记录之间的空间 防止插入新记录
临键锁 记录锁 + 间隙锁 同时保护已有记录和插入空间

整个逻辑可以表示为：

text

↓
快照读
↓
MVCC
↓
Read View 判断版本是否可见
↓
沿版本链找到可见版本
↓
读取该版本的数据


SELECT ... FOR UPDATE
UPDATE
DELETE
↓
当前读
↓
读取最新可操作版本
↓
根据索引扫描范围加锁
↓
Record Lock / Gap Lock / Next-Key Lock
↓
限制其他事务修改或插入

最终可以记住两句话：

Read View 决定“当前事务应该读取哪个版本”

锁机制决定“其他事务现在能不能修改或插入数据”

因此，InnoDB 在 RR 隔离级别下，是通过 MVCC + Read View 处理快照读，通过记录锁、间隙锁、临键锁等机制处理当前读，两者共同避免幻读

# 当前读与快照读

类型 常见 SQL 读取方式
快照读 普通 SELECT 根据 Read View 判断版本可见性，必要时沿 undo log 版本链找旧版本
当前读 SELECT ... FOR UPDATE、SELECT ... FOR SHARE、UPDATE、DELETE 读取当前最新可操作版本，并进行加锁

版本链只是记录了数据的可见与不可见，不同版本之间数据的可见性不同，但数据的存在与否于版本链无关

# 小表驱动大表：JOIN 优化

多表连接时，需要尽量减少连接过程中参与计算的数据量，例如：

SQL 
SELECT *
FROM small_table s
JOIN large_table l
    ON s.user_id = l.user_id;

传统上经常使用：

小表驱动大表

其核心思想并不是简单地规定“小表必须写在前面”，而是：

尽量让外层处理的数据量更少，并让被匹配的一侧具有合适索引

例如：

text 
小表：100 行
大表：100 万行

如果能够先处理小表中的少量记录，再利用大表的索引查找：

text 
小表 100 行
↓
每一行通过索引查大表
↓
快速定位对应记录

通常比大量扫描更加高效，不过需要注意：

MySQL 优化器会根据统计信息自动选择 JOIN 顺序，并不完全取决于 SQL 中表的书写顺序

因此 JOIN 优化更应该关注：

text 
参与连接的数据量
+
JOIN 字段是否有索引
+
WHERE 条件能否提前过滤数据
+
实际执行计划

而不能机械地认为：

text 
FROM 小表 JOIN 大表

就一定更快

# 模拟面试题

# 为什么联合索引 (name, age) 必须优先知道 name，才能高效地利用 age？请从 B+ 树中数据的排序方式解释，而不是只回答“因为最左前缀原则”

因为B+树对于联合索引存放的数据进行排序时，首先对name进行排序，当name相同时，再对age进行排序，此时age并不是全局有序的，因此若缺失name只对age进行索引时，索引失效，可能会进行全表扫描

你这段回答里的核心逻辑是完整的：

text 
联合索引 (name, age)

先按 name 排序
↓
name 相同时
↓
再按 age 排序

所以 age 只是局部有序，不是全局有序。缺少 name 这个前提时，就不能直接根据 age = 20 快速定位到一个连续的索引范围

有一个表达细节建议修正：

“只对 age 进行索引时，索引失效”

更准确应说：

“只根据 age 查询时，这个 (name, age) 联合索引通常无法被用于高效定位”

因为 age 本身并没有单独创建索引，所以不是“age 索引失效”，而是联合索引无法充分利用
