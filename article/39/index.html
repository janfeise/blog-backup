# 1. 为什么动态路由不能直接生成 HTML

vite-ssg 无法知道动态路由具体有哪些，以博客来说，vite-ssg 无法知道每一篇博客的路由有哪些，因此无法为每篇博客生成静态HTML文档

在传统 SPA 中，/article/38 这类地址只是前端路由的运行时结果。浏览器进入页面后，Vue Router 根据当前路径渲染对应组件，但构建阶段并不知道最终会访问哪些文章 ID，所以静态构建默认只能生成一个路由壳，而不能自动生成 /article/38/index.html、/article/37/index.html 这类页面。

# 核心原因

  • 动态路由的参数来自运行时数据
  • 构建时没有提前知道文章列表
  • 普通 Vite 构建只会产出单页应用资源，不会枚举业务数据

也就是说，/article/:id 是“路由规则”，不是“具体页面路径”。如果不额外告诉构建器哪些路径需要渲染，就不会生成对应 HTML。

# 2. vite-ssg 是怎么工作的

vite-ssg 的目标是把 Vue 应用从 SPA 转成“可以静态预渲染的应用”。它的工作流程大致分为三步：

  1. 先构建客户端资源，生成可在浏览器运行的 JS/CSS
  2. 再构建服务端渲染资源，生成用于 SSR 的临时入口
  3. 根据路由列表逐个渲染页面，把 HTML 写入 dist

在博客场景里，vite-ssg 的关键价值是：

  • 首页、关于页、文章详情页都能提前生成 HTML
  • 搜索引擎可以直接读取内容
  • 首屏速度更好，尤其是文章页

# 你需要理解的两个概念

# SSG

Static Site Generation，静态站点生成。构建时把页面渲染成 HTML。

# SSR

Server Side Rendering，服务端渲染。这里主要用于“构建时的预渲染阶段”，不是在线服务端渲染。

在 vite-ssg 中，SSR 和 SSG 是配合使用的：

  • SSR 负责在构建时执行组件逻辑、拉取数据、生成 HTML
  • SSG 负责把这些 HTML 固化到 dist 目录

# 3. includedRoutes 的作用

includedRoutes 是 vite-ssg 提供的路由筛选和扩展机制。它解决的正是“构建时不知道该生成哪些动态路由”的问题。

它的职责很直接：

  • 接收当前已有的路由路径 paths
  • 接收路由记录 routes
  • 返回最终需要参与静态生成的路径列表

在博客项目中，它的作用就是：

  • 构建时先请求文章列表接口，获取所有文章的id
  • 从 records 中提取文章 ID
  • 组装成 /article/38、/article/37 这样的真实路径
  • 让 vite-ssg 在预渲染时逐个生成 HTML

# 4. 项目中的路由结构

当前项目的路由采用“数组导出”的方式，而不是直接在 router/index.js 中创建路由实例。这样更适合 vite-ssg 使用。

# 路由入口

js 
// src/router/index.js
import articleRouter from "./modules/article";
import aboutRouter from "./modules/about";

const routes = [
  {
    path: "/",
    name: "Home",
    component: () => import("@/views/Home/index.vue"),
  },
  ...articleRouter,
  ...aboutRouter,
];

export default routes;

# 文章路由

js 
// src/router/modules/article.js
const articleRouter = [
  {
    path: "/article/:id",
    name: "ArticleDetail",
    component: () => import("@/views/Article/ArticleView.vue"),
  },
];

export default articleRouter;

这里的关键点是：/article/:id 只是规则，真正参与预渲染的必须是 includedRoutes 返回的 /article/38 这种具体路径。

# 5. main.js 的完整配置方式

这是当前项目的核心入口配置，也是整个静态化链路的中心。

js 
// src/main.js
import { ViteSSG } from "vite-ssg";
import ElementPlus, {
  ID_INJECTION_KEY,
  ZINDEX_INJECTION_KEY,
} from "element-plus";
import "element-plus/dist/index.css";
import { createPinia } from "pinia";
import piniaPluginPersistedstate from "pinia-plugin-persistedstate";

import { getArticles } from "@/api/blog";
import App from "./App.vue";
import routes from "./router";

import "./styles/main.scss";

export const createApp = ViteSSG(App, { routes }, ({ app, router }) => {
  app.provide(ID_INJECTION_KEY, { prefix: 1024, current: 0 });
  app.provide(ZINDEX_INJECTION_KEY, { current: 0 });

  app.use(router);
  app.use(ElementPlus);

  const pinia = createPinia();
  if (!import.meta.env.SSR) {
    pinia.use(piniaPluginPersistedstate);
  }
  app.use(pinia);
});

export async function includedRoutes(paths, routes) {
  try {
    const res = await getArticles();
    const articleRecords = res?.data?.records || [];
    const articlePaths = articleRecords.map(
      (article) => `/article/${article.id}`,
    );

    return routes.flatMap((route) => {
      if (route.name === "ArticleDetail") return articlePaths;
      return route.path;
    });
  } catch (error) {
    console.error("获取文章列表失败，使用默认路由生成静态页面：", error);
    return paths;
  }
}

# 这段代码做了什么

  • ViteSSG(...) 把 Vue 应用交给 vite-ssg 管理
  • ID_INJECTION_KEY 和 ZINDEX_INJECTION_KEY 解决 Element Plus SSR 注入问题
  • piniaPluginPersistedstate 只在客户端启用
  • includedRoutes 动态注入文章页面路径

# 6. onServerPrefetch 的执行时机

onServerPrefetch 只会在 SSR 阶段执行，它的作用是：

  • 在服务端渲染组件之前提前拉取数据
  • 确保 HTML 生成时已经有内容
  • 避免“先渲染空壳、客户端再补数据”

在文章详情页中，它的时机非常关键：

  1. 路由解析出 /article/38
  2. SSR 进入 ArticleView.vue
  3. onServerPrefetch 触发 loadArticle(route.params.id)
  4. 文章数据写入响应式状态
  5. 最终渲染出包含正文的 HTML

这就是为什么它比 onMounted 更适合 SSG/SSR 预取。

# 为什么不能只用 onMounted

onMounted 只在客户端执行，SSR 阶段不会运行。这样构建出来的 HTML 只会是空壳，搜索引擎和首屏体验都会变差。

# 7. ArticleView.vue 的完整配置方式

文章详情页是动态路由静态化是否成功的关键。

vue 
<!-- src/views/Article/ArticleView.vue -->
<script setup>
import { ref, watch, onServerPrefetch } from "vue";
import { useRoute, useRouter } from "vue-router";
import articleLayout from "@/Layout/article/articleLayout.vue";
import MarkdownRenderer from "@/components/MarkdownRenderer.vue";
import ArticleTableOfContents from "@/components/ArticleTableOfContents.vue";
import { getArticleById } from "@/api/blog";
import { ElMessage } from "element-plus";
import articleList from "./components/articleList.vue";

const route = useRoute();
const router = useRouter();
const article = ref(null);
const loading = ref(true);
const tableOfContents = ref([]);

const loadArticle = async (id) => {
  loading.value = true;

  try {
    const res = await getArticleById(id);

    if (res?.status !== 200) {
      article.value = null;
      if (!import.meta.env.SSR) {
        ElMessage.error(res?.message || "文章加载失败");
      }
      return;
    }

    article.value = res.data;

    if (!import.meta.env.SSR) {
      if (!route.hash) {
        window.scrollTo({ top: 0, left: 0, behavior: "smooth" });
      } else {
        const rawHash = route.hash.substring(1);
        if (!rawHash) return;

        const targetId = decodeURIComponent(rawHash);
        setTimeout(() => {
          const element = document.getElementById(targetId);
          if (element) {
            element.scrollIntoView({ behavior: "smooth" });
          }
        }, 100);
      }
    }
  } catch (error) {
    if (!import.meta.env.SSR) {
      ElMessage.error("获取文章失败，请检查网络连接");
    }
  } finally {
    loading.value = false;
  }
};

const handleMarkdownReady = () => {
  console.log("Markdown 渲染完成");
};

const handleTOCChange = (toc) => {
  tableOfContents.value = toc;
};

const handleTOCClick = (id) => {
  router.replace({ hash: `#${id}` });
};

watch(
  () => route.params.id,
  (id) => {
    loadArticle(id);
  },
  { immediate: !import.meta.env.SSR },
);

// 通过 onServerPrefetch 等待接口返回数据
onServerPrefetch(async () => {
  await loadArticle(route.params.id);
});
</script>

# 为什么这样写

  • watch(..., { immediate: !import.meta.env.SSR })：避免 SSR 和预取阶段重复请求
  • onServerPrefetch：确保服务端预渲染时拿到文章内容
  • import.meta.env.SSR：区分服务端和客户端
  • window / document 仅在客户端使用

# 8. SSR 与客户端环境的区别

SSR 环境和浏览器环境最大的区别，是 SSR 没有浏览器对象。

# SSR 中不存在的对象

  • window
  • document
  • localStorage
  • sessionStorage
  • 部分依赖 DOM 的第三方组件行为

# 正确的判断方式

js 
if (!import.meta.env.SSR) {
  window.scrollTo({ top: 0 });
}

# 错误示例

js 
window.scrollTo({ top: 0 });

如果这段代码在 SSR 阶段执行，就会直接报错：

text 
ReferenceError: window is not defined

# 正确示例

js 
if (!import.meta.env.SSR) {
  window.scrollTo({ top: 0 });
}

同理，访问 document.getElementById(...)、localStorage.getItem(...) 也必须做同样的保护。

# 9. Pinia 持久化插件在 SSR 中的兼容处理

本项目使用了 pinia-plugin-persistedstate，它默认依赖浏览器环境中的存储能力。如果在 SSR 阶段直接安装，会触发 window is not defined。

# 错误示例

js 
app.use(createPinia().use(piniaPluginPersistedstate));

# 正确示例

js 
const pinia = createPinia();

if (!import.meta.env.SSR) {
  pinia.use(piniaPluginPersistedstate);
}

app.use(pinia);

# 原理说明

  • SSR 阶段只负责渲染，不应依赖浏览器存储
  • 客户端阶段再启用持久化，才能安全访问 localStorage

# 10. Element Plus 在 vite-ssg 中为什么需要 ID_INJECTION_KEY 和 ZINDEX_INJECTION_KEY

Element Plus 的部分组件会在 SSR 场景下生成 ID、处理浮层层级和 teleport。若没有提供注入值，就会出现 hydration 相关警告。

# 为什么需要 ID_INJECTION_KEY

它用于保证服务端和客户端生成的 ID 一致，避免 hydration mismatch。

# 为什么需要 ZINDEX_INJECTION_KEY

它用于给弹层、对话框、提示框等组件提供统一的初始 z-index 基线。

# 错误示例

js 
app.use(ElementPlus);

# 正确示例

js 
app.provide(ID_INJECTION_KEY, { prefix: 1024, current: 0 });
app.provide(ZINDEX_INJECTION_KEY, { current: 0 });
app.use(ElementPlus);

# 会出现什么警告

text 
ElementPlusError: [IdInjection] Looks like you are using server rendering...
ElementPlusError: [ZIndexInjection] Looks like you are using server rendering...

这类警告说明 Element Plus 组件在 SSR 场景中缺少必要上下文。

# 11. scss 报错的根本原因与修复方案

# 问题现象

构建时出现：

text 
TypeError [ERR_UNKNOWN_FILE_EXTENSION]: Unknown file extension ".scss"

# 根本原因

项目最初在 unplugin-vue-components 的 Element Plus Resolver 中使用了 importStyle: "sass"，会把按需组件样式指向 theme-chalk/src/*.scss。

在客户端构建中，Vite 会处理这些 SCSS；但在 vite-ssg 的 server 构建阶段，Node 会尝试直接加载这些源文件，结果就报错了。

# 错误示例

js 
ElementPlusResolver({
  importStyle: "sass",
});

# 正确示例

js 
ElementPlusResolver({
  importStyle: false,
});

并且保留全局 CSS：

js 
import "element-plus/dist/index.css";

# 为什么这样修复有效

  • 不再让 SSR 阶段去解析 .scss
  • 改为引入已经编译好的全局 CSS
  • 避免 Node 直接处理样式源文件

# 12. 构建流程解析

# 第一步：客户端构建

vite-ssg 先构建客户端资源，生成 dist/assets/* 中的 JS 和 CSS。

# 第二步：服务端构建

再构建 SSR 临时入口，用于真正执行组件逻辑和预渲染。

# 第三步：includedRoutes 获取文章路径

构建时执行：

  1. 请求 GET /articles
  2. 读取 data.records
  3. 将文章 ID 转成 /article/:id
  4. 返回给 vite-ssg

# 第四步：逐页 SSR 渲染

vite-ssg 会对以下路径分别执行渲染：

  • /
  • /about
  • /article/1
  • /article/2
  • /article/3
  • …

# 第五步：输出 HTML

最终在 dist 目录下生成对应 HTML。

# 13. 动态文章路径生成流程

文章页的 SSR 渲染顺序如下：

# 16. 常见问题分析

# 16.1 为什么没有生成文章 HTML

通常是因为没有正确实现 includedRoutes，或者 includedRoutes 没有返回文章详情路径。

# 错误示例

js 
export async function includedRoutes(paths) {
  return paths;
}

# 正确示例

js 
export async function includedRoutes(paths, routes) {
  const res = await getArticles();
  const articlePaths = res.data.records.map(
    (article) => `/article/${article.id}`,
  );

  return routes.flatMap((route) => {
    if (route.name === "ArticleDetail") return articlePaths;
    return route.path;
  });
}

# 16.2 为什么 onServerPrefetch 没有执行

常见原因：

  • 写在了 onMounted
  • 组件没有真正参与 SSR 渲染
  • 路由没有被 includedRoutes 包含

# 错误示例

js 
onMounted(() => {
  loadArticle(route.params.id);
});

# 正确示例

js 
onServerPrefetch(async () => {
  await loadArticle(route.params.id);
});

# 16.3 为什么动态路由不会自动预渲染

因为 /article/:id 只是路由模式，不是路径列表。vite-ssg 无法凭空知道文章 ID，必须通过 includedRoutes 显式告诉它。

# 16.4 为什么会出现 Unknown file extension “.scss”

原因是 Element Plus 按需样式导入把 SCSS 源文件暴露给了 SSR 构建。修复方式是关闭 importStyle: "sass"，改为全局 CSS。

# 16.5 为什么会出现 window is not defined

原因是在 SSR 环境直接访问了 window、document、localStorage 或使用了依赖这些对象的插件。

正确处理方式是：

js 
if (!import.meta.env.SSR) {
  // browser-only code
}

# 17. vite-ssg 按目录式输出

vite-ssg 默认会把路由 /article/39 输出为扁平文件形式，也就是 dist/article/39.html。这个形式在本地预览时通常没有问题，但在很多静态服务器或站点部署环境中，用户直接访问 /article/39 时，服务器会优先去寻找目录式页面，例如 /article/39/index.html。如果部署环境没有额外配置 URL 重写规则，就可能找不到对应资源，从而出现“文章页面访问失败”的问题。

换句话说，问题不在于文章没有被渲染出来，而在于“URL 访问路径”和“静态文件组织方式”不一致。为了让 /article/39 这种路由能够自然命中静态文件，应该把输出结构改成目录式，也就是：

  • /article/39 -> dist/article/39/index.html
  • /about -> dist/about/index.html

# 配置方式

在 vite.config.js 中配置：

js 
ssgOptions: {
  dirStyle: "nested",
},

# 配置效果

配置为 dirStyle: "nested" 后，vite-ssg 会把每个路由页面输出为“目录 + index.html”的形式。这样无论是本地静态预览还是部署到常见的静态托管平台，都更容易让 /article/39 这类 URL 正确命中页面。

# 18. 实践结论

在博客项目中使用 vite-ssg 做动态路由静态化，关键不是“把路由写出来”，而是让构建阶段知道“要生成哪些具体页面”，并且让页面在 SSR 阶段能够安全执行数据预取。

这套方案的核心组合是：

  • includedRoutes：负责把动态路由展开成真实路径
  • onServerPrefetch：负责在 SSR 阶段提前拿到页面数据
  • import.meta.env.SSR：负责区分服务端与客户端代码
  • Pinia 客户端持久化：避免 SSR 访问浏览器 API
  • Element Plus SSR 注入：避免 hydration 和层级警告
  • 全局 CSS 引入：避免 SCSS 在 SSR 阶段被 Node 直接加载

把这些环节串起来之后，博客项目就可以稳定地在构建阶段生成每一篇文章的静态 HTML，同时保持客户端交互能力。
