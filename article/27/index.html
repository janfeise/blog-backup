# AList 本地挂载与媒体存储实践

背景：通过 1Panel 面板部署 AList，由于采用 Docker 容器方式运行，因此需要先完成目录挂载，才能实现文件持久化与本地存储管理

在实际使用过程中，如果不理解容器挂载机制，很容易遇到“文件丢失”“路径不存在”“回收站报错”等问题。本文将结合实践，系统梳理 AList 本地挂载的完整流程，并给出推荐架构方案

# 挂载

在 1Panel 面板左侧菜单栏找到「容器」，选择 AList 容器并进行编辑，添加挂载目录

需要理解一点：

挂载的本质，是将容器内的目录映射到服务器目录，后续即使容器删除，数据仍保留在所挂载的服务器目录下

也就是说：

text 
容器目录 ≠ 实际存储位置

当你完成挂载后：

  • 容器内的文件 → 实际存储在服务器
  • 容器删除后 → 数据仍然存在（不会丢失）

# AList 添加本地存储

完成挂载后，需要在 AList 后台添加“本地存储”

操作步骤：

  1. 进入 AList 管理后台
  2. 添加存储 → 选择「本地存储」
  3. 在“根文件夹路径”中填写容器内路径（注意不是服务器路径）

例如：

text 
/opt/alist/data/blog-images

# 常见问题说明

在使用过程中，最容易踩的坑是：

# 回收站报错：invalid cross-device link

原因在于：

AList 删除文件时使用的是 rename 操作

而 Linux 中：

text 
rename 只能在同一个文件系统中执行

如果你的“存储目录”和“回收站目录”分别挂载到不同磁盘，就会出现该问题

# 推荐系统架构

为了避免上述问题，同时方便后续扩展（图床、画廊、视频管理），建议采用统一挂载方案。

# 核心思路

  • 只挂载一个根目录
  • 所有媒体资源统一管理
  • 回收站与存储目录必须在同一挂载点

# 具体实现

# 宿主机目录

bash 
/data/blog-media/

# 容器挂载

text 
容器目录：/opt/alist/data/blog
宿主机目录：/data/blog-media

# 容器内目录结构

bash 
/opt/alist/data/blog/
├── blog-images/
├── blog-garbage/

说明：

  • blog-images：存储图片资源
  • blog-garbage：作为回收站

# AList 配置

在 AList 后台设置：

text 
根文件路径：/opt/alist/data/blog/blog-images
回收站路径：/opt/alist/data/blog/blog-garbage

# 效果展示

# 避免跨磁盘问题

  • 存储目录与回收站在同一文件系统
  • 不再出现 rename 报错

# 数据结构清晰

  • 所有媒体资源统一在 /data/blog-media
  • 方便备份与迁移

# 易于扩展

后续可以直接扩展：

bash 
/data/blog-media/
├── images/
├── videos/
├── garbage/
├── thumbs/

用于支持：

  • 图床系统
  • 博客图片管理
  • 画廊页面
  • 视频资源管理

# 总结

在使用 AList 进行本地存储时，核心不是“如何挂载”，而是：

如何设计一个稳定、可扩展的存储结构

关键要点可以归纳为：

  • 容器挂载优先使用“单一根目录”
  • AList 路径必须使用容器内路径
  • 回收站与存储目录必须在同一文件系统
  • 提前规划媒体目录结构，避免后期迁移成本

当这些基础设计做好后，AList 不仅可以作为文件管理工具，还可以进一步演变为：

个人图床 + 媒体资源中心 + 博客资源管理系统

这也是后续构建完整内容平台的重要基础
