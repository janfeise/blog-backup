前端表单校验与校验规则

阅读时间约 27 分钟 · 字数 5216

# 前端表单校验与自定义校验梳理

在日常开发中，使用 ant-vue 组件库的 a-form 表单组件时涉及到表单的校验与自定义校验的需求，在此做一个梳理

  • 基础校验配置 rules 即可满足要求

  • 当上一条内置规则无法表达时，才需要自定义校验；如：联动校验（两次密码是否一致）、异步接口校验等

但，大多数场景并不需要手写自定义校验函数，rules 中配置的基础规则已经能完成大量“通用校验”。

# 基础校验

基础校验通过配置 rules 即可，例如：

JS 
const rules = {
  password: [{ required: true, type: 'string', min: 8, max: 20, message: "请输入密码" }]
}

这里配置了：

  • 必填校验
  • 字符串类型校验
  • 最小长度校验
  • 最大长度校验

那么，如何触发校验并显示提示信息（“请输入密码”）呢？——为 a-form 组件绑定 ref

vue 
<template>
	<a-form ref="formRef" :rules="rules"> <!-- 关键！！！ -->
    	<a-form-item lable="密码" name="password"></a-form-item>
    </a-form>
	
	<a-form-item>
      <a-button type="primary" @click="handleSubit">Submit</a-button>
    </a-form-item>
</template>
<!-- lable是表单在页面显示的文本；name需与rules中对应的字段一一对应 -->

通常情况下，点击按钮 submit 触发校验，校验通过再进行后续的处理

js 
const formRef = ref(null)

const handleSubmit = () => {
    try {
        await formRef.value.validate()
    } catch {
        message.warning('校验失败，请XXX')
        return
    }
    
    // 后续逻辑
}

通过 formRef.value.validate() 即可触发校验，需要注意的是，validate() 本质是异步校验，因此通常需要配合 await 使用。

# 同一个字段可配置多个 rule

rules 的能力其实非常强大，同一个字段可以配置多个规则。

例如用户名：

js 
username: [
  { required: true, message: '请输入用户名' },
  { min: 3, max: 20, message: '长度 3-20 位' },
  { pattern: /^[a-zA-Z0-9_]+$/, message: '只能包含字母数字下划线' }
]

其执行逻辑大致可以理解为：

text 
必填校验
→ 长度校验
→ 正则格式校验

这也是为什么很多场景下无需编写自定义校验函数，仅依赖 rules 即可完成大部分需求。

在配置 rules 时，还有一个常用的参数：trigger

# trigger 触发时机

在配置 rules 时，还有一个非常常用的参数：trigger。

它用于指定：

text 
什么时候触发当前规则

例如：

js 
trigger: 'blur'
trigger: 'change'
trigger: ['blur', 'change']

含义如下：

trigger 含义
blur 失焦触发
change 值变化触发
[‘blur’,‘change’] 两者都触发

例如：

js 
{
  required: true,
  message: '请输入用户名',
  trigger: 'blur'
}

表示：

text 
当输入框失焦时触发校验

# 常见内置规则

以下是 a-form 中常见的内置规则：

规则 作用
required 必填
type 类型校验
min 最小长度 / 最小值
max 最大长度 / 最大值
len 固定长度
pattern 正则校验
enum 枚举值
whitespace 空白字符校验

其中：

js 
whitespace: true // 禁止全空白字符，全空白字符校验会失败

是一个容易被忽略但非常实用的规则。

例如：

js 
{
  required: true,
  whitespace: true,
  message: '请输入用户名'
}

它不仅会校验空字符串：

js 
''

还会校验：“全空格”输入

js 
'     '

因此，在文本输入场景中，通常推荐搭配使用。

# 自定义校验

当上述基础校验仍无法满足需求时，才考虑自定义校验，如：

  • 联动校验（两次密码是否一致）

  • 异步接口校验等

# 联动校验示例：两次密码一致

模板代码如下：

vue 
<a-form ref="formRef" :rules="rules" :model="formState"> <!-- 关键 formState -->
    <a-form-item lable="密码" name="password1"></a-form-item>

    <a-form-item lable="确认密码" name="password2"></a-form-item>

    <a-form-item>
          <a-button type="primary" @click="handleSubit">Submit</a-button>
    </a-form-item>
</a-form>
<!-- lable是表单在页面显示的文本；name需与rules中对应的字段一一对应 -->

此时需校验：两次输入的密码是否一致，基础校验无法做到跨 field 校验，因此需手动编写自定义校验；

这里有一个关键点：

js 
:model="formState"

因为联动校验本质上属于：

text 
跨字段访问

因此需要把多个字段统一放在同一个响应式对象中：

js 
const formState = reactive({
  password: '',
  confirmPassword: ''
})

# 自定义 validator 实现

确认密码校验函数如下：

js 
/**
 * 确认密码校验
 */
const validateConfirmPassword = async (_rule, value) => {
  // 未输入
  if (!value) {
    return Promise.reject('请再次输入密码')
  }

  // 不一致
  if (value !== formState.password) {
    return Promise.reject('两次密码输入不一致')
  }

  return Promise.resolve()
}

# rules 配置

js 
const rules = {
  password: [{ required: true, message: "请输入密码", trigger: "blur" }],
  confirmPassword: [{ validator: validateConfirmPassword, trigger: "blur" }],
};

这里与基础校验最大的区别在于：

js 
validator: validateConfirmPassword

即：

text 
当前规则使用自定义校验函数

# 提交时触发校验

js 
const handleSubmit = () => {
    try {
        await formRef.value.validate()
    } catch {
        message.warning('校验失败，请XXX')
        return
    }
    ...
}

当点击按钮时：

js 
formRef.value.validate()

会自动执行：

  • 基础规则
  • 自定义 validator

只要其中任意一项失败，就会进入 catch。

# validator 的标准结构

js 
const validator = (_rule, value) => {}

参数：

参数 含义
rule 当前规则对象，大多数场景无用，但可以读取 rule 中的配置信息，只在一些特殊场景使用
value 当前字段值

例如：

js 
validator(_, value)

这里：

js 
value = confirmPassword 当前输入值

# rule 参数的作用

很多时候会看到：

js 
(_, value)

或者：

js 
(_rule, value)

这是因为：

text 
大多数场景并不需要使用 rule

因此会用 _ 表示：

text 
“该参数存在，但当前逻辑未使用”

不过，rule 在一些高级场景中依然非常有价值。

例如：

js 
{
  min: 5,
  max: 10,
  validator(rule, value) {
    console.log(rule.min)
    console.log(rule.max)
  }
}

此时可以动态读取规则配置，实现：

  • 通用校验器
  • 动态规则系统
  • 公共 validator 封装

因此：

text 
大多数业务场景只使用 value
高级封装场景才会频繁使用 rule

# 总结

在 a-form 表单校验中，一个比较推荐的开发思路是：

text 
优先使用内置 rules
→ 再考虑 validator
→ 最后再处理复杂联动逻辑

很多情况下：

text 
required
min
max
pattern
type

已经足够完成绝大多数表单校验需求。

只有在：

text 
跨字段
联动逻辑
异步接口
复杂业务规则

等场景下，才真正需要使用自定义 validator。

合理利用基础规则，不仅代码更简洁，也能降低维护成本，提高表单代码的可读性与可维护性。
