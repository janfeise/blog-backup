# 常见注解

按照 Spring Boot 开发时的分层结构记忆：

注解 作用
@Controller 标注控制层组件，负责处理 HTTP 请求
@Service 标注业务逻辑层组件，负责处理业务逻辑
@Repository 标注数据访问层组件，负责数据库访问

# HTTP 请求映射注解

由于在 controller 层往往会处理 http 请求，根据不同的请求方法选择对应的 service 层，因此有以下常见的注解：

注解 作用
@GetMapping 处理 GET 请求，通常用于查询数据
@PostMapping 处理 POST 请求，通常用于新增数据
@PutMapping 处理 PUT 请求，通常用于更新数据
@DeleteMapping 处理 DELETE 请求，通常用于删除数据

# HTTP 响应注解

Controller 层处理完请求后，需要将结果返回给客户端，通常以 JSON 格式返回。

  • @Controller：默认将方法返回的字符串视为视图名称，通过视图解析器查找并渲染对应页面（如 HTML）
  • @ResponseBody：将方法返回值直接写入 HTTP 响应体，不进行视图解析。返回 Java 对象时，通常会自动序列化为 JSON
  • @RestController：相当于 @Controller + @ResponseBody，默认将方法返回值写入 HTTP 响应体，适用于前后端分离开发（restful api）

核心区别： @Controller 默认偏向视图解析，而 @RestController 默认直接返回响应数据。

# @Controller 示例

只使用 @Controller 注解，会将返回的字符串进行视图解析，返回对应的HTML

java 
@Controller
public class UserController {

    @GetMapping("/user")
    public String user() {
        return "user";
    }
}

这里返回的 "user" 并不是直接发送给浏览器，而是作为视图名称，由 Spring MVC 的视图解析机制处理

例如使用 Thymeleaf 时，可以解析到：

java 
src/main/resources/templates/user.html

然后渲染 HTML 页面并返回给浏览器；如果要返回 JSON，可以添加 @ResponseBody 注解：

java 
@Controller
public class UserController {

    @ResponseBody
    @GetMapping("/user")
    public User user() {
        return new User(1, "张三");
    }
}

Spring MVC 会通过合适的 HttpMessageConverter 将对象序列化，常见情况下使用 Jackson 转换为 JSON

# HTTP 请求参数注解

  • @RequestBody：用于接收前端传递的 JSON 数据

前端发送 post 请求：

json 
{
  "name": "张三",
  "age": 20
}

后端接受数据：@RequestBody 注解

java 
@RestController
public class UserController {

    @PostMapping("/user")
    public String addUser(@RequestBody User user) { // RequestBody 接受前端传递的JSON数据

# 依赖注入注解

  • @Autowired：Spring 提供的依赖注入注解，默认按照类型从 IoC 容器中查找 Bean 并注入

# @Autowired 注解与 @Resource 注解的区别

可以通过 @Autowired 与 @Resource 注入 Bean 到对应属性中，但存在不同：

  1. @Autowired 是 Spring 提供的注解，@Resource 是 java EE 标准提供的注解

  2. 两者都用于依赖注入，核心区别在于匹配方式：

  • @Autowired 默认按类型匹配，同类型存在多个 Bean 时，可以结合名称等条件进一步筛选
  • @Resource 默认先按名称匹配，未指定名称且名称匹配失败时，再按类型匹配

# spring 核心组成模块

  • spring-core 与 spring-beans：提供 IoC 容器的基础实现，管理 Bean 的创建与装配
  • spring-web：web应用初始化
  • spring-context：应用上下文，好像是企业级功能
  • spring-test：提供 JUnit 单元测试等

# IOC与DI

IoC（控制反转，Inversion of Control），就是由 Spring 容器来控制和管理对象，不用手动进行 new 创建，以及销毁

DI：由于对象都交由 Spring 容器管理，后续使用对象时进行依赖注入即可

# 依赖注入方式有哪些？

  1. 构造函数注入：通过类的构造函数来注入依赖项。
  2. Setter 注入：通过类的 Setter 方法来注入依赖项。
  3. Field（字段） 注入：直接在类的字段上使用注解（如 @Autowired 或 @Resource）来注入依赖项。

构造函数注入示例：

java 
@Service
public class UserService {

    private final UserRepository userRepository; // final 修饰

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    //...
}

Setter 注入示例：

java 
@Service
public class UserService {

    private UserRepository userRepository;

    @Autowired
    public void setUserRepository(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    //...
}

Field 注入示例：

java 
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    //...
}

# 构造函数注入与setter注入的区别是？

  • 依赖完整性：构造函数注入要求在创建对象时就提供必须依赖，而 setter 注入可以在创建对象后再设置依赖
  • 不可变性：构造函数注入通常配合 final 修饰依赖字段，避免后续被重新赋值
  • 适用场景：两者适用场景不同，构造函数注入适合必须依赖，而 setter 注入则适合可选依赖

记忆重点：构造函数注入 = 必需依赖 + final；Setter 注入 = 可选依赖 + 可重新设置

构造函数注入示例：

java 
@Service
public class UserService {

    private final UserRepository userRepository; // final

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    //...
}

Setter 注入示例：

java 
@Service
public class UserService {

    private UserRepository userRepository;

    @Autowired
    public void setUserRepository(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    //...
}

两者使用时的差别：构造函数注入是“创建时传入依赖”，Setter 注入是“创建后设置依赖”

java 
// 构造函数注入：创建对象时必须传入依赖
UserService service = new UserService(userRepository);

// Setter 注入：先创建对象，再设置依赖
UserService service = new UserService();
service.setUserRepository(userRepository);

需要注意：以上两种写法是为了说明 Java 对象的创建方式。在实际 Spring 开发中，通常由 Spring 容器负责创建对象并完成依赖注入，而不是手动 new

# Bean 的生命周期

Spring Bean 的生命周期类似于 Vue 组件的生命周期，开发者可以在不同阶段执行对应的业务逻辑，例如初始化资源、释放资源等

视频：一个例子讲明白 Spring Bean 的生命周期

# Bean 生命周期的主要阶段

Spring Bean 的生命周期可以简化为以下 5 个阶段：

  1. 实例化：Spring 容器创建 Bean 实例
  2. 属性赋值：Spring 为 Bean 注入所需的依赖，例如通过 Setter 方法或字段注入
  3. 初始化：依赖注入完成后，执行初始化逻辑，例如 @PostConstruct 或配置的 initMethod
  4. 使用：Bean 初始化完成后，可以被其他组件使用，执行业务逻辑
  5. 销毁：Spring 容器关闭时，执行销毁回调，例如 @PreDestroy 或配置的 destroyMethod，用于释放资源

其中，常见的生命周期注解有：

注解 执行时机 主要用途
@PostConstruct 依赖注入完成后 初始化资源、加载配置
@PreDestroy Bean 销毁前 关闭连接、释放资源

注意：上述是简化后的生命周期，实际还涉及 Bean 后置处理器等机制

# Bean 生命周期示例

首先，定义一个依赖组件：

java 
@Component
public class TaskRepository {

    public void save() {
        System.out.println("执行数据保存");
    }
}

然后，定义业务组件 TaskService，通过 Setter 方法注入 TaskRepository：

java 
@Component
public class TaskService {

    private TaskRepository taskRepository;

    // 1. 实例化
    public TaskService() {
        System.out.println("1. Bean 实例化");
    }

    // 2. 属性赋值
    @Autowired
    public void setTaskRepository(TaskRepository taskRepository) {
        this.taskRepository = taskRepository;
        System.out.println("2. Bean 属性赋值");
    }

    // 3. 初始化，等价于 initMethod
    @PostConstruct
    public void init() {
        System.out.println("3. Bean 初始化");
    }

    // 4. 使用
    public void execute() {
        System.out.println("4. Bean 使用");
        taskRepository.save();
    }

    // 5. 销毁
    @PreDestroy
    public void destroy() {
        System.out.println("5. Bean 销毁");
    }
}

上述代码需要导入对应的注解：@Component、@Autowired、@PostConstruct 和 @PreDestroy

调用 Bean：

java 
@Component
public class TaskRunner implements CommandLineRunner {

    private final TaskService taskService;

    public TaskRunner(TaskService taskService) {
        this.taskService = taskService;
    }

    @Override
    public void run(String... args) {
        taskService.execute();
    }
}

运行结果：

text 
1. Bean 实例化
2. Bean 属性赋值
3. Bean 初始化
4. Bean 使用
执行数据保存

当 Spring Boot 应用正常关闭时：

text 
5. Bean 销毁

注意：示例以默认单例 Bean 为前提，仅展示主要生命周期阶段，实际 Spring 内部还涉及 Bean 后置处理器等机制

# 面试总结

Spring Bean 的生命周期主要包括 实例化、属性赋值、初始化、使用和销毁 五个阶段

其中，构造函数注入在实例化阶段完成，而 Setter 注入和字段注入通常在属性赋值阶段完成

开发者可以使用 @PostConstruct 在初始化阶段执行相关逻辑，使用 @PreDestroy 在销毁前释放资源

# 单例 bean 的线程安全问题

Spring bean 的作用域默认是单例 bean，即 Spring 容器只会存在一个 Bean 实例，并且该实例会被多个线程共享，因此在多线程情景下可能存在问题

  • 如果单例 Bean 是无状态的，没有成员变量，那么这个单例 Bean 是线程安全的，比如 Spring MVC 中的 controller、service、dao等，基本都是无状态的
  • 如果 Bean 内部有成员变量，在多线程情景下会存在线程安全问题

单例 Bean存在多线程安全问题，常见的有三种解决办法：

  1. 优先设计无状态 Bean：避免使用可变的共享成员变量，尽量使用方法局部变量
  2. 必要时进行线程同步：例如使用 synchronized、AtomicInteger 等机制
  3. 使用 ThreadLocal：对于确实需要线程隔离的数据，可以使用 ThreadLocal，但需要注意线程池环境下的数据清理与内存泄漏风险。

# Bean 的作用域有哪些？

Spring 中 Bean 的作用域通常有下面几种：

  • singleton：单例，Ioc 容器中只存在唯一的 Bean 实例。Spring 中的 bean 默认都是单例的，是对单例模式的应用
  • prototype：原型，每次获取都会创建一个新的 bean 实例。也就是说 getBean() 两次，得到的是不同的 Bean 实例
  • request（仅web应用可用）：每一次http请求都会产生一个新的 bean（请求bean），该 bean 仅在当前http request 内有效
  • session（仅web应用可用）：每一次来自新 session 的 http 请求都会产生一个新的 bean（会话bean），该 bean 仅在当前 http session 有效

如何配置 bean 的作用域呢？

xml 方式：

xml 
<bean id="..." class="..." scope="singleton"></bean>

注解方式：

java 
@Bean
@Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public Person personPrototype() {
    return new Person();
}

# 三级缓存解决循环依赖

# 什么是循环依赖？

在 Spring 中，依赖注入主要有三种方式：构造器注入、Setter 注入、Field 字段注入。

其中，Setter 注入与 Field 字段注入的特点是：Bean 的实例化与属性赋值分开进行，先创建对象，再注入依赖，这为解决循环依赖提供了条件。

例如：

java 
@Component
public class CircularDependencyA {
    @Autowired
    private CircularDependencyB circB;
}

@Component
public class CircularDependencyB {
    @Autowired
    private CircularDependencyA circA;
}

此时：

  • A 依赖 B，需要先获取 B
  • B 依赖 A，需要先获取 A

两者相互依赖，形成循环依赖

# Spring 如何解决循环依赖？

Spring 通过三级缓存机制，提前暴露尚未完成属性赋值和初始化的 Bean，从而解决部分循环依赖问题。

首先了解三级缓存：

缓存 名称 存储内容
一级缓存 singletonObjects 完成初始化的单例 Bean
二级缓存 earlySingletonObjects 提前暴露的 Bean 引用
三级缓存 singletonFactories 用于获取提前暴露 Bean 引用的工厂

以 A、B 循环依赖为例，结合 Bean 生命周期进行分析：

具体步骤：

  1. 实例化 A：创建 A 对象，并将用于获取 A 提前引用的工厂放入三级缓存
  2. A 属性赋值：发现依赖 B，于是开始创建 B
  3. 实例化 B：创建 B 对象，同样将其工厂放入三级缓存
  4. B 属性赋值：发现依赖 A，此时通过三级缓存获取 A 的提前引用，并将该引用放入二级缓存，完成 B 对 A 的注入
  5. 完成 B：B 完成初始化，进入一级缓存
  6. 完成 A：将 B 注入 A，A 完成初始化，进入一级缓存

至此，A 和 B 的循环依赖得到解决。

# 为什么需要三级缓存？

  • 一级缓存：保存已经完成初始化的单例 Bean
  • 二级缓存：保存提前暴露的 Bean 引用，避免重复创建提前引用
  • 三级缓存：保存 ObjectFactory，在需要时获取 Bean 的提前引用，支持提前生成 AOP 代理对象

需要注意：三级缓存的关键作用之一是配合 AOP，保证循环依赖场景下能够获取合适的代理对象引用。如果只考虑普通对象之间的循环引用，并非一定需要三级缓存。

# 哪些循环依赖无法解决？

Spring 的三级缓存并不能解决所有循环依赖：

  • 构造器循环依赖：A 创建时需要 B，B 创建时又需要 A，此时 A 尚未实例化，无法提前暴露引用
  • Prototype 多例 Bean 循环依赖：Spring 不会像单例 Bean 一样对其进行三级缓存管理
  • 部分复杂场景：例如某些 Bean 后置处理器或代理创建场景，仍可能出现循环依赖异常

此外，Spring Boot 2.6 起默认禁止循环依赖，即使是可以通过三级缓存处理的循环依赖，也可能直接报错。可以通过 spring.main.allow-circular-references=true 允许尝试处理，但实际开发中更推荐从设计上消除循环依赖。

# 面试总结

说说三级缓存如何解决循环依赖的？

我觉得解决循环依赖主要与依赖注入方式有关，依赖注入有三种方式：构造函数注入、setter 注入、field字段注入，setter注入与字段注入的核心点便是实例化与属性赋值分离，基于这里，在bean进行初始化时将循环依赖的对象放置在三级缓存中，存放提前引用的工厂，后续循环依赖可以直接从三级缓存中获取所需的依赖，完成初始化，至于另一个循环依赖的bean，此时也能进行后续的属性赋值和初始化。因此，对于构造函数产生的循环依赖往往无法进行解决

一级缓存存储完成初始化的单例 Bean，二级缓存存储提前暴露的 Bean 引用，三级缓存存储获取提前引用的工厂，并支持 AOP 代理的提前生成。

需要注意，构造器循环依赖和 Prototype 多例 Bean 的循环依赖通常无法通过该机制解决。

# AOP

aop：面向切面编程，实现了主业务与分支业务的解耦，主业务无需关心日志记录等操作，这些操作都统一通过aop进行实现和记录

spring 是如何实现 aop 的？——动态代理，JDK动态代理与cglib动态代理，那么两者有什么区别？

# jdk动态代理和cglib代理的区别

JDK 动态代理和 CGLIB 代理的主要区别在于实现方式。

JDK 动态代理基于接口，通过实现目标接口生成代理对象，而

CGLIB 代理基于继承，通过创建目标类的子类生成代理对象，因此不要求目标对象实现接口。但是由于 Java 中 final 类不能被继承，final 方法不能被重写，所以 CGLIB 无法代理 final 类，也无法增强 final 方法。

记忆要点：JDK 基于接口，CGLIB 基于继承；CGLIB 受 final 限制。

# 三级缓存是如何处理代理对象的？

在 spring 中，无论是 jdk 动态代理，还是 cglib 代理，两者的共同特点都是——通过 代理对象 实现增强，对于普通循环依赖二级缓存便足以，但代理却不行

# 为什么普通循环依赖只需要二级缓存？

假设存在两个 Bean：

java 
@Component
public class A {
    @Autowired
    private B b;
}

@Component
public class B {
    @Autowired
    private A a;
}

Spring 创建 Bean A 时：

  1. 实例化 A，此时 A 尚未完成属性注入
  2. 将 A 提前放入缓存
  3. 给 A 注入 B，发现 B 尚未创建，开始创建 B
  4. 给 B 注入 A，从缓存中获取提前暴露的 A
  5. B 创建完成，注入 A，最终 A 创建完成

在这个过程中，只需要：

  • 一级缓存：存放初始化完成的 Bean
  • 二级缓存：存放提前暴露、尚未完成初始化的 Bean

因此，对于不涉及代理的常见 Setter/字段注入循环依赖，理论上二级缓存就足够了。

# 为什么 aop 代理需要特殊处理

aop 代理是通过代理对象实现，二级缓存会绕过代理

假设 A 需要进行 AOP 增强：

java 
@Component
public class A {
    @Autowired
    private B b;

    @Transactional
    public void doSomething() {
        System.out.println("执行事务方法");
    }
}

JDK 动态代理和 CGLIB 虽然实现方式不同，但有一个共同点：

代理对象与原始对象不是同一个对象。

  • JDK 动态代理：创建实现目标接口的代理对象
  • CGLIB：创建目标类的子类作为代理类，并生成代理对象，通过方法拦截实现增强

假设 A 的原始对象为 A_original，代理对象为 A_proxy。

如果 B 注入的是 A_original，而 Spring 最终对外提供的是 A_proxy，那么就会出现问题：

text 
B.a  → A_original（原始对象）
容器 → A_proxy（代理对象）

这样 B 调用 A 的方法时，就可能绕过 AOP 增强，例如 @Transactional 无法按预期生效。

因此，Spring 必须确保：B 提前获取的 A，与容器最终对外提供的 A，是同一个代理对象。

# 二级缓存处理aop循环依赖会出现什么问题？

假设 A 依赖 B，B 又依赖 A。

Spring 首先创建 A：

text 
① 实例化 A_original
          ↓
② A 需要注入 B
          ↓
③ 开始创建 B
          ↓
④ B 又需要注入 A
          ↓
⑤ 此时 A 还没有完成初始化

问题就在第⑤步：

如果直接把原始对象 A_original 注入 B，就会变成：

B 持有的是原始对象，其他 Bean 从容器中获取的却是代理对象。这不仅可能绕过 AOP 增强，还可能造成 Bean 引用不一致。

# 三级缓存处理aop循环依赖

Spring 不会直接把原始对象 A 放到三级缓存，而是先放入一个 ObjectFactory。

当 B 需要 A 时，才调用工厂中的 getEarlyBeanReference()。

可以把它理解为下面这段简化的伪代码：

java 
Object getEarlyBeanReference(Object bean) {
    if (需要AOP代理(bean)) {
        return 创建代理对象(bean);
    }

    return bean;
}

假设 A 需要代理，那么：

text 
B 需要 A
    ↓
从三级缓存获取 ObjectFactory
    ↓
调用 getEarlyBeanReference(A_original)
    ↓
提前获取 A_proxy
    ↓
把 A_proxy 放入二级缓存
    ↓
将 A_proxy 注入 B

最终得到：

text 
B.a       → A_proxy
Spring容器 → A_proxy

这样 B 调用 A 的方法时，也能够经过代理对象，执行事务等 AOP 增强。

如果 A 不需要 AOP 代理，getEarlyBeanReference() 通常直接返回 A_original 即可。

# Spring MVC的工作流程

工作流程：从前端发起请求，到后端处理请求并返回给前端的整个过程

  1. 接收请求：前端发送 HTTP 请求，由 DispatcherServlet 统一接收
  2. 处理器映射：DispatcherServlet 调用 HandlerMapping，根据请求路径、请求方法等条件找到对应的处理器，并返回 HandlerExecutionChain（包含处理器和拦截器）
  3. 处理器执行：DispatcherServlet 调用 HandlerAdapter，由适配器执行拦截器的前置处理，并调用对应的 Controller 方法处理业务
  4. 返回结果：Controller 执行完成后，传统 MVC 模式通常返回 ModelAndView，包含模型数据和视图信息
  5. 视图解析与渲染：DispatcherServlet 调用 ViewResolver 解析视图，再渲染视图并将响应返回客户端

速记：

Spring MVC 的核心是 DispatcherServlet。首先接收前端请求，通过 HandlerMapping 找到对应的处理器执行链，然后由 HandlerAdapter 调用 Controller 执行业务逻辑。传统 MVC 模式会返回 ModelAndView，包含模型数据和视图信息，最后通过 ViewResolver 解析视图并渲染返回。

# spring 如何实现事务

通过 aop 代理进行实现，对方法前后进行拦截，执行方法前开启事务，执行完目标方法后根据情况进行提交或者回滚事务

java 
@Transactional(rollbackFor = Exception.class)
public void createOrder() {
    // 1. 创建订单
    orderMapper.insert();

    // 2. 扣除余额
    accountMapper.deductBalance();

    // 3. 模拟异常
    int result = 1 / 0;
}

代理对象：

java 
public void proxyCreateOrder() {
    // 获取事务并根据传播行为开启或加入事务
    TransactionStatus status = transactionManager.getTransaction(definition);

    try {
        // 执行目标方法
        target.createOrder();

        // 正常执行，提交事务
        transactionManager.commit(status);

    } catch (Throwable e) {
        // 仅演示 rollbackFor = Exception.class 的常见效果
        if (e instanceof Exception) {
            transactionManager.rollback(status);
        } else {
            transactionManager.commit(status);
        }

        throw e;
    } finally {
        // 事务资源清理由事务管理器负责
    }
}

注意：以上只是原理示意，并非 Spring 的实际源码。真实的 Spring 事务拦截器会先区分目标方法异常与提交过程异常，并根据回滚规则、传播行为和事务状态进行处理。

# 事务失效的场景有哪些？

添加 @Transactional 注解后事务失效的场景有哪些？

Spring 声明式事务主要通过 AOP 动态代理 + 事务管理器实现，因此分析事务失效时，可以从两个角度考虑：

  1. AOP 代理是否生效：目标方法有没有经过代理对象？
  2. 事务回滚条件是否满足：方法执行过程中发生异常，Spring 是否能够感知并触发回滚？

# 1. private 修饰的方法导致事务失效

Spring 通过代理对象进行事务增强，private 方法是无法进行代理

例如：

java 
@Service
public class OrderService {

    @Transactional
    private void createOrder() {
        orderMapper.insert();
        accountMapper.deductBalance();
    }
}

这里 private 方法无法被 Spring 默认的 AOP 代理进行事务增强。

解决方案： 建议将事务方法声明为 public，并确保通过 Spring 管理的代理对象调用。

java 
@Transactional
public void createOrder() {
    orderMapper.insert();
    accountMapper.deductBalance();
}

为了保证跨版本、跨代理方式的一致性，开发中一般推荐在 public 方法上使用 @Transactional。

# 2. 异常被捕获，没有向上抛出

原因： Spring 事务拦截器需要感知异常，才能根据回滚规则执行回滚。如果业务方法自己捕获并处理异常，事务拦截器通常会认为方法正常执行完成，从而提交事务。

例如：

java 
@Transactional
public void createOrder() {
    try {
        orderMapper.insert();
        accountMapper.deductBalance();

        int result = 1 / 0;
    } catch (Exception e) {
        e.printStackTrace(); // 捕获异常
    }
}

执行流程：

  1. Spring 开启事务
  2. 执行插入订单和扣除余额
  3. 发生 ArithmeticException
  4. catch 捕获异常，没有继续向外抛出
  5. 方法正常结束，Spring 提交事务

解决方案： 在 catch 中重新抛出异常。

java 
@Transactional
public void createOrder() {
    try {
        orderMapper.insert();
        accountMapper.deductBalance();

        int result = 1 / 0;
    } catch (Exception e) {
        throw new RuntimeException(e); // 抛出异常
    }
}

这样 Spring 就能够感知异常，并根据回滚规则执行回滚。

补充：也可以使用 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() 手动标记事务回滚，但通常更推荐合理地向上抛出异常。

# 3. 抛出非runtime异常与error异常时，事务失效

原因： Spring 默认仅对 RuntimeException 和 Error 触发回滚，对于普通受检异常，如 IOException、FileNotFoundException，默认不会回滚。

例如：

java 
@Transactional
public void createOrder() throws IOException {
    orderMapper.insert();
    accountMapper.deductBalance();

    throw new IOException("文件读取失败");
}

虽然方法抛出了异常，但默认配置下 Spring 仍然会尝试提交事务。

解决方法：配置 rollbackFor 属性 @Transactional(rollbackFor=Exception.class)，该属性会对 Exception 及其子类回滚，同时保留对 Error 的默认回滚

java 
@Transactional(rollbackFor = Exception.class)
public void createOrder() throws IOException {
    // 1. 创建订单
    orderMapper.insert();

    // 2. 扣除余额
    accountMapper.deductBalance();

    // 3. 抛出受检异常
    throw new IOException("文件读取失败");
}

执行结果：

  • 执行创建订单
  • 执行扣除余额
  • 抛出 IOException
  • Spring 根据 rollbackFor 配置回滚整个事务
  • 创建订单和扣除余额操作均被撤销

# 4. 同一个类内部的方法调用

一个类中方法B添加了事务，方法A去调用方法B，但是方法A没有添加事务，此时方法A不会触发事务，也不会生成代理对象，导致事务失效

原因： Spring 默认通过 AOP 代理对象实现事务增强，而同一个类内部通过 this 调用其他方法时，不会再次经过代理对象，因此被调用方法上的 @Transactional 不会单独生效。

例如：

java 
@Service
public class OrderService {

    public void methodA() {
        methodB();
    }

    @Transactional
    public void methodB() {
        orderMapper.insert();
        accountMapper.deductBalance();
    }
}

# spring 事务传播机制

Spring 事务传播机制（Propagation）主要用于解决：当一个事务方法调用另一个事务方法时，被调用的方法应该如何处理事务？

例如，存在两个 Service：

  • OrderService：负责创建订单，对应事务 A
  • AccountService：负责扣除余额，对应事务 B
java 
@Service
public class OrderService {

    @Autowired
    private AccountService accountService;

    @Transactional
    public void createOrder() {
        // 1. 创建订单
        orderMapper.insert();

        // 2. 扣除余额
        accountService.deductBalance(); // 另一个事务方法

        // 3. 模拟异常
        int result = 1 / 0;
    }
}

@Service
public class AccountService {

    @Transactional
    public void deductBalance() {
        accountMapper.deductBalance();
    }
}

这里存在一个问题：createOrder() 调用了另一个带有 @Transactional 的方法，那么两个方法的事务应该如何执行？

主要有三种处理方式：

  • 融入：加入外层事务
  • 挂起：两个事务相互独立，互不影响
  • 嵌套：类似于保存点

MySQL 不支持真正独立的嵌套事务，但 InnoDB 支持 SAVEPOINT 保存点。因此 Spring 在适当的事务管理器配置下，可以通过保存点实现 NESTED 的嵌套回滚语义。

# 四种核心事务传播机制

传播机制 外层有事务 外层无事务
REQUIRED 加入已有事务 创建新事务
REQUIRES_NEW 挂起外层，创建新事务 创建新事务
SUPPORTS 加入已有事务 以非事务方式执行
MANDATORY 加入已有事务 抛出异常

以下仍然使用创建订单和扣除余额的案例，分别说明四种机制。

# REQUIRED：加入已有事务（默认）

java 
@Transactional(propagation = Propagation.REQUIRED)
public void deductBalance() {
    accountMapper.deductBalance();
}
  • 外层有事务：加入外层事务，共同提交或回滚
  • 外层无事务：自己创建一个新事务

结合案例： createOrder() 开启事务 A，deductBalance() 加入事务 A。当外层执行 1 / 0 发生异常时，订单创建和余额扣除都会回滚。

可以理解为：两个方法共享同一个数据库事务。

# REQUIRES_NEW：挂起外层事务，创建新事务

java 
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void deductBalance() {
    accountMapper.deductBalance();
}
  • 外层有事务：挂起外层事务，开启独立的新事务
  • 外层无事务：直接创建新事务

结合案例：

  1. createOrder() 开启事务 A，插入订单
  2. 调用 deductBalance()，挂起事务 A
  3. 创建事务 B，扣除余额并提交事务 B
  4. 恢复事务 A
  5. 执行 1 / 0，事务 A 回滚

结果：订单创建回滚，但余额扣除已提交，不会随事务 A 回滚。

原因是事务 A 与事务 B 属于独立的物理事务，可以分别提交或回滚。

在常见的 JDBC 本地事务中，事务 A 和事务 B 通常使用不同的数据库连接。使用时需要注意连接池大小，避免连接资源不足。

# SUPPORTS：有事务就加入，没有就不创建

java 
@Transactional(propagation = Propagation.SUPPORTS)
public void deductBalance() {
    accountMapper.deductBalance();
}
  • 外层有事务：加入外层事务，与 REQUIRED 类似
  • 外层无事务：不创建事务，直接执行

结合案例： 因为 createOrder() 已经开启事务 A，所以 deductBalance() 会加入事务 A。当外层异常回滚时，余额扣除也随之回滚。

但如果直接调用 deductBalance()，并且没有已存在的事务，那么方法将以非事务方式执行。对于开启自动提交的数据库连接，单条 SQL 通常会各自提交。

与 REQUIRED 的区别： 无外层事务时，REQUIRED 会创建事务，而 SUPPORTS 不会。

# MANDATORY：必须存在事务

必须存在事务，不存在则抛出异常

java 
@Transactional(propagation = Propagation.MANDATORY)
public void deductBalance() {
    accountMapper.deductBalance();
}
  • 外层有事务：加入外层事务
  • 外层无事务：直接抛出异常，不执行目标方法

结合案例： createOrder() 已经开启事务 A，因此 deductBalance() 可以正常加入事务 A。

如果直接从没有事务的地方调用 deductBalance()，Spring 就会抛出事务相关异常（通常为 IllegalTransactionStateException）。

与 SUPPORTS 的区别： 无外层事务时，SUPPORTS 允许执行，而 MANDATORY 禁止执行。

# 补充：NESTED 嵌套事务

虽然不属于你重点记忆的四种传播机制，但可以将 NESTED 和 REQUIRES_NEW 对比理解。

java 
@Transactional(propagation = Propagation.NESTED)
public void deductBalance() {
    accountMapper.deductBalance();
}
  • 外层有事务：在当前事务中创建保存点，允许回滚内层操作
  • 外层无事务：行为类似 REQUIRED，创建新事务

例如：

java 
@Transactional
public void createOrder() {
    orderMapper.insert();

    try {
        accountService.deductBalance();
    } catch (Exception e) {
        // 处理扣款失败
    }
}

假设 deductBalance() 使用 NESTED，且扣款过程中抛出了符合回滚规则的异常，那么：

  1. 事务 A 开始，创建订单
  2. 进入嵌套事务，在事务 A 中设置保存点
  3. 扣款失败，回滚到保存点
  4. 外层捕获异常，继续执行
  5. 事务 A 正常提交，订单创建保留

这与 REQUIRES_NEW 的区别在于：NESTED 并没有创建独立物理事务。如果外层事务 A 最终回滚，内层已完成的修改也会一起回滚。

MySQL InnoDB 支持保存点，因此可以配合 Spring 的 JDBC 事务管理器实现这种行为，但并非所有事务管理器都支持 NESTED。
