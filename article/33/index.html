预渲染 vite-ssg

阅读时间约 29 分钟 · 字数 5706

在使用 Vue3 构建博客时，默认产出的是一个典型的 SPA（单页面应用）。这种模式在交互体验上非常流畅，但对搜索引擎并不友好。由于页面内容依赖JavaScript 执行后才渲染出来，搜索引擎在抓取时可能拿不到完整内容，从而影响收录与排名

为了解决这个问题，通常会引入预渲染或 SSG 方案。对于博客这类“结构相对稳定、动态内容有限”的页面，可以在构建阶段提前生成 HTML 文件。这样一来，搜索引擎可以直接解析完整内容，既提升了首屏加载速度，也增强了 SEO 表现

不过，这种方式也带来了一个绕不开的问题：构建时生成的内容是“过去的快照”，当数据在构建之后发生变化，用户访问的仍然是旧的静态内容，那么如何在保证性能的同时，又确保数据的实时性

解决方案：预渲染 + 客户端请求

# 预渲染 + 客户端请求

一种非常实用的解决方案是将“静态生成”和“动态更新”结合起来使用

整体流程如下：

  1. 预渲染生成初始 HTML（用于首屏展示与 SEO），其中包含的是构建时的数据
  2. 浏览器加载页面并执行 JavaScript
  3. 前端主动发起 API 请求获取最新数据
  4. 使用最新数据替换页面中的旧内容

可以用一段简单代码来说明这一过程：

js 
import { ref, onMounted } from 'vue'

export default {
  setup() {
    const posts = ref([])

    onMounted(async () => {
      const res = await fetch('/api/posts')
      posts.value = await res.json()
    })

    return { posts }
  }
}

页面初始渲染时使用的是<u>预渲染阶段的数据</u>，而在组件挂载后，会通过接口请求获取最新内容，并自动更新视图

由于在开发中，数据都是动态生成的，因此只需实现了预渲染，后续的数据会自动获取，替换旧的数据，那么当你的数据变化很大时，需要重新进行一次预渲染，生成新的静态页面

预渲染的价值更多体现在：

  • 提供一个可被搜索引擎识别的初始 HTML
  • 提升首屏加载速度
  • 优化用户首次访问体验

而数据的实时性，则交由客户端请求来保证

以博客首页举例，首页展示的文章是动态从服务器获取的，当你的文章有很大的变化时，需从新进行预渲染构建由于在开发中，数据都是动态生成的，因此只需实现了预渲染，后续的数据会自动获取，替换旧的数据，那么当你的数据变化很大时，需要重新进行一次预渲染，生成新的静态页面 以博客首页举例，首页展示的文章是动态从服务器获取的，当你的文章有很大的变化时，需从新进行预渲染构建

# vite-ssg 的基本使用流程

vite-ssg 是基于 Vite 和 Vue3 的静态站点生成工具，在构建阶段生成对应路由的 HTML 文件

  1. 下载依赖

    bash 
    npm i -D vite-ssg vue-router @vueuse/head

  2. 配置 package.json

    json 
    "build": "vite-ssg build",

  3. main.js 引入

    • 需导出 createApp
    • 禁止导入 createApp：报错 [PARSE_ERROR] Error: Identifier createApp has already been declared
    js 
    // import { createApp } from "vue"; // 不用导入
import { ViteSSG } from "vite-ssg

export const createApp = ViteSSG(
  App,
  { routes },
  ({ app, router, routes, isClient }) => {
    // 注册插件
    app.use(router);

    // 也可以在这里做更多初始化逻辑
  },
);

  4. 路由配置：需导出 routes

    • Vite-SSG 路由只需要定义 routes即可, 不要使用 createRouter创建了路由！！否则会出现报错
    • 只需要导出 routes，不需要创建 router 实例
    js 
    const routes = [
  {
    path: "/",
    name: "home",
    component: () => import("../views/Home.vue"),
  },
  {
    path: "/about",
    name: "about",
    component: () => import("../views/About.vue"),
  },
  ...

]

// 不用创建
// const router = createRouter({
//   history: createWebHistory(),
//   routes
// })

export default routes

  5. 构建，在命令行运行：

    bash 
    npm run build

构建后会生成如下结构：在 dist 生成了对应路由的静态页面

txt 
dist/
├── .vite/
├── assets/
├── about.html
├── contact.html
├── favicon.ico
└── index.html

这些 HTML 文件就是部署时服务器直接返回的内容

# 构建阶段的数据获取

默认情况下，vite-ssg 不会等待接口返回，而是直接生成静态页面。如果希望在构建时拿到数据，可采用以下两种方案：

  • onServerPrefetch：是vue专门为 SSR 设计的钩子，会拦截渲染过程，强制要求组件在 onServerPrefetch 执行完之前，**阻塞（Block）**后续的渲染
  • pinia：状态管理，vite-ssg 对它有原生支持。你可以把请求逻辑写在 Pinia 的 action 中

onServerPrefetch：

文档：https://cn.vuejs.org/api/composition-api-lifecycle#onserverprefetch

这个钩子仅会在服务端渲染中执行，可以用于执行一些仅存在于服务端的数据抓取过程

  • onServerPrefetch 是一个vue的生命周期钩子，它必须在 setup 的同步执行阶段直接注册，而<u>不能嵌套在其他函数（如 onMounted 或异步函数内部）里</u>
vue 
<script setup>
import { onServerPrefetch } from "vue";
    
const src = ref(""); // 图片src

// 在服务端构建时执行
onServerPrefetch(async () => {
  console.log("正在构建渲染..."); // 构建时你会在终端看到这个
  await loadImage(); // 从服务器获取图片src
});
</script>

构建完成后，HTML 中已经包含接口返回的数据：

html 
 </p><img src="https://picsum.photos/200/300" alt="Loaded Image">

src 是异步从服务器获取的，通过 onServerPrefetch 会等待接口的数据返回，然后再生成静态的html

这一步保证了页面在首屏时就是完整内容

# 数据过时问题的本质

当使用 onServerPrefetch 时，接口数据会被直接写入 HTML 文件

示例：

vue 
<script setup>
const data = ref();

// 模拟接口返回数据
const fetchData = async () => {
  const res = await new Promise((resolve) =>
    setTimeout(() => resolve(Math.random()), 1000),
  );
  data.value = res;
};
    
onServerPrefetch(async () => {
  console.log("正在构建渲染..."); // 构建时你会在终端看到这个
  await loadImage();
});
</script>

<template>
	<h3>{{ data }}</h3>
</template>

构建所生成的静态html中，数据如下：

html 
<h3>0.4909592787792021</h3>

这个值在构建完成后就被固定下来，因此它一定是旧数据，问题不在于 vite-ssg，而在于构建行为本身是一次性的，那么应该如何处理呢？此时我们需要知道网站访问流程！

服务器返回静态HTML -> 客户端激活运行vue，重新执行代码

# 网站访问流程

背景：将 vite-ssg 打包的文件部署在服务器，那么用户访问网站的流程是什么呢？

阶段 A：静态呈现（Static Rendering）

用户访问页面时，服务器直接返回对应的 HTML 文件

  • 优点： 极快，因为不需要服务器运行任何 JS，也不需要等待 API 返回
  • 缺点： 页面内容在**下一次构建（Build）**之前，永远固定在那个时刻

阶段 B：客户端激活（Hydration）

虽然返回的是静态 HTML，但生成的 assets/*.js 文件依然会在浏览器中运行，浏览器加载 JS 后，Vue 应用开始运行，并对已有 HTML 进行激活

  1. Vue 启动应用

  2. 执行组件的 setup 逻辑

  3. 触发生命周期函数（如 onMounted）

  4. 如果存在接口请求，则重新获取数据并更新页面

因此，页面其实经历了一个过程：

先展示旧数据，然后被新数据覆盖

# 何时需要重新预渲染

虽然客户端可以保证数据更新，但在某些情况下，仍然需要重新执行预渲染构建

例如：

  • 首页文章结构发生明显变化（如分页、排序规则调整）
  • 文章数量大幅增长，影响初始渲染内容
  • SEO 需要更新（如标题、描述、关键词）

以博客首页为例，文章列表通常是从服务器动态获取的。如果只是新增几篇文章，客户端请求即可覆盖旧数据；但如果内容规模或结构发生较大变化，就需要重新执行一次预渲染，生成新的静态 HTML

总结：

预渲染并不是为了“让数据永远静态”，而是为了在性能与动态性之间取得平衡

它解决的是“如何更快、更好地展示页面”，而不是“如何实时更新数据”

将预渲染与客户端请求结合使用，既能保证页面的加载速度和 SEO 表现，又不会牺牲数据的实时性，这也是博客类项目中最常见且实用的一种实践方式

# SSG 和组件库

在实际开发中，项目通常会引入组件库来提升开发效率与界面一致性。在使用 vite-ssg 进行构建时，这些组件库本身是可以正常打包进产物中的，并不会受到影响

不过需要注意的是，构建生成的 dist 目录本质上是一个完整的静态站点，而不是可以通过直接双击 HTML 文件来运行的本地页面。若直接在浏览器中打开 HTML 文件，可能会出现样式丢失、资源加载失败或组件功能异常等问题

这是因为组件库及其依赖的资源通常通过模块化路径加载，需要依赖一个正确的 HTTP 服务环境

如果希望在本地预览构建结果，应当启动一个静态服务器。在项目根目录下执行以下命令：

bash 
# 使用 npm 自带的工具启动预览
npx serve dist

通过这种方式访问页面，资源路径与运行环境将与实际部署保持一致，组件库也能够正常加载与运行
