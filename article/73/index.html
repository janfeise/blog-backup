# JVM、JRE、JDK

JAVAGUID-java基础

JVM：Java 虚拟机（Java Virtual Machine, JVM）是运行 Java 字节码的虚拟机。JVM 有针对不同系统的特定实现（Windows，Linux，macOS），目的是使用相同的字节码，它们都会给出相同的结果。字节码和不同系统的 JVM 实现是 Java 语言“一次编译，随处可以运行”的关键所在。

JRE：Java Runtime Environment，JRE 是运行已编译 Java 程序所需的环境，主要包含以下两个部分：

  1. JVM : 也就是我们上面提到的 Java 虚拟机。
  2. Java 基础类库（Class Library）：一组标准的类库，提供常用的功能和 API（如 I/O 操作、网络通信、数据结构等）。

JDK（Java Development Kit）是一个功能齐全的 Java 开发工具包，供开发者使用，用于创建和编译 Java 程序。它包含了 JRE（Java Runtime Environment），以及编译器 javac 和其他工具，如 javadoc（文档生成器）、jdb（调试器）、jconsole（监控工具）、javap（反编译工具）等。

我觉得主要区别在于代码的复用性，与前端的JavaScript不同，JavaScript通过原型链实现复用，而Java则主要通过类的继承实现，子类继承父类的方法，因此包装类可以使用父类的方法，如：map、filter……，但基本类型不行

# 为什么重写 equals() 时必须重写 hashCode()

参考：Java equals() 和 hashCode() 详解

# equals() 方法

equals() 定义在 Java 的 Object 类中，默认通过 == 判断两个引用是否指向同一个对象

Java 
public boolean equals(Object obj) {
    return this == obj;
}

但实际开发中，我们可能希望两个不同对象的属性相同，也认为它们相等，因此需要重写 equals()

例如：

Java 
Person p1 = new Person("Tom", 20);
Person p2 = new Person("Tom", 20);

System.out.println(p1 == p2);      // false
System.out.println(p1.equals(p2)); // true（重写 equals 后）

重写示例：

Java 
@Override
public boolean equals(Object obj) {
    if (this == obj) return true; // 同一个对象

    if (obj == null || getClass() != obj.getClass())
        return false;

    Person person = (Person) obj;

    return age == person.age
            && Objects.equals(name, person.name); // 不同对象比较属性是否相同
}

# hashCode() 方法

hashCode() 同样定义在 Object 类中，用于返回对象的哈希码（int 类型），主要用于 HashSet、HashMap 等哈希集合，辅助快速定位元素，以 HashSet 为例，底层基于 HashMap 实现，添加元素时：

  1. 计算哈希值：调用 hashCode()，经过处理后确定数组桶的位置
  2. 检查桶内元素：
    • 桶为空：直接插入
    • 桶不为空：检查已有节点的哈希码
    • 哈希码相同：进一步通过 == 或 equals() 判断是否相等
  3. 决定是否插入：
    • 存在相等元素：拒绝插入
    • 不存在相等元素：插入新节点

注意：不同哈希码也可能映射到同一个桶，但不会因此直接调用 equals() 比较

# 为什么重写 equals() 必须重写 hashCode()

假设 Person 只重写了 equals()，没有重写 hashCode()

Java 
Person p1 = new Person("Tom", 20);
Person p2 = new Person("Tom", 20);

System.out.println(p1.equals(p2)); // true

HashSet<Person> set = new HashSet<>();
set.add(p1);
set.add(p2);

System.out.println(set.size()); // 可能为 2

问题原因：

  • p1 和 p2 属性相同，equals() 返回 true
  • 但默认 hashCode() 通常根据对象身份生成哈希码，两者可能不同
  • HashSet 根据不同哈希码定位元素，可能将两个对象都插入集合，导致去重失败

解决方法：同时重写 hashCode()，使用与 equals() 相同的属性计算哈希码

Java 
@Override
public int hashCode() {
    return Objects.hash(name, age);
}

此时：

Java 
p1.equals(p2);                    // true
p1.hashCode() == p2.hashCode();   // true

HashSet 就能正确识别两个逻辑上相等的对象，最终 set.size() 为 1

总的来说，重写 hashCode 是为了处理当两个对象相同时，哈希表不重复添加元素

# 总结

  • equals()：判断两个对象在逻辑上是否相等
  • hashCode()：生成哈希码，帮助哈希表快速定位对象
  • 重写 equals() 时必须同时重写 hashCode()，保证相等对象具有相同哈希码
  • hashCode() 相同不代表对象相等，仍需通过 equals() 进一步判断

核心：equals() 负责判断对象是否相等，hashCode() 负责辅助定位对象，两者必须遵守一致的相等性规则，才能保证哈希集合正常工作

# String、Stringbuilder、Stringbuffer

文档：https://javaguide.cn/java/basis/java-basic-questions-02.html#⭐️-string、stringbuffer、stringbuilder-的区别

都是用来处理字符串的，但 String 不可变，每次修改都会生成新的对象，并将引用指向新的实例（即新的String），而 StringBuffer 和 StringBuilder 都是可变的，它们在修改字符串时不会创建新对象，而是直接在原有字符数组上进行操作。

因此，遇到大量字符串连接可以用 StringBuilder ，不会生成许多新的对象，StringBuilder 与 StringBuffer 的区别是，StringBuffer 对字符串的基本操作，如：append、insert 等都添加了同步锁，synchronized，线程安全，而 StringBuilder 并没有对方法进行加同步锁，所以是非线程安全的。

String 为什么不可变？——final

  • 在源码中，java对于 String 类的保存通过数组存储每个字符，并通过 final 进行修饰，而且没有提供/暴露修改这个字符串的方法
  • String 类也被 final 修饰，导致其不能被继承，进而避免了子类破坏 String 不可变
java 
public final class String implements java.io.Serializable,Comparable<String>, CharSequence {
    // @Stable 注解表示变量最多被修改一次，称为“稳定的”。
    @Stable
    private final byte[] value;
}

# 反射

在程序运行时，可以动态的获取类的属性与方法，并可以调用方法，例如：

java 
User user = new User();
user.sayHello();

编译时已经明确知道调用的是 User 类的 sayHello() 方法。而通过反射：

java 
Class<?> clazz = Class.forName("com.example.User");

# IO流

Java IO（Input / Output）流用于实现程序与外部数据源（如文件、网络等）之间的数据读取与写入，IO 流主要有两种分类方式：

  • 按照数据流向划分
    • 输入流：从外部读取数据到程序，如 InputStream、Reader
    • 输出流：从程序向外部写入数据，如 OutputStream、Writer
  • 按照数据处理单位划分
    • 字节流：以字节（8 bit）为单位处理数据，如 InputStream、OutputStream
    • 字符流：以字符为单位处理数据，如 Reader、Writer

# 字节流与字符流的区别

计算机实际存储的数据是二进制数据。对于文本，程序需要根据字符编码规则（如 ASCII、UTF-8、UTF-16）将字节数据转换为字符，或将字符转换为字节

两者的核心区别在于处理数据的单位不同，以及是否涉及字符编码与解码

  • 字节流：以字节为单位读取或写入数据，不直接处理字符编码，适用于图片、视频、音频等二进制数据，也可以处理文本
  • 字符流：以字符为单位读取或写入数据，适用于文本处理，通常需要在底层字节数据与字符之间进行编码或解码

例如，使用 UTF-8 编码时：

字符 UTF-8 编码 占用字节数
A 41 1 字节
中 E4 B8 AD 3 字节
😀 F0 9F 98 80 4 字节

因此：

  • 字节流读取字符 中 对应的 UTF-8 数据，需要读取 3 个字节才能获取完整的编码数据
  • 字符流通过字符解码器将这 3 个字节转换为 Java 字符数据，而不需要开发者手动组合字节

注意： Java 的 Reader.read() 每次读取的是一个 UTF-16 代码单元（返回 int），并不保证每次都能读取一个完整的 Unicode 字符。例如，😀 在 Java 中需要两个 char 表示

# 总结

字节流直接处理原始字节，字符流处理文本字符，并在需要时完成字符编码与解码

  • 处理二进制文件：优先使用字节流
  • 处理文本文件：优先使用字符流，并明确指定字符编码（如 UTF-8）

# 在 IO 中，文件字节流读取时返回值类型为什么是 int？

在 Java IO 中，InputStream.read() 每次读取 1 个字节（8 bit），但返回值类型为 int（32 bit）

核心原因：使用 -1 表示文件读取结束（EOF），避免与实际读取的数据产生冲突

# 为什么不使用 byte？

Java 中的 byte 是有符号类型，取值范围为 -128～127，而一个字节有 256 种可能的二进制组合

如果返回值类型为 byte，则无法区分实际数据与文件结束标志：

  • 读取到字节 11111111：按照 Java 的有符号 byte 解释，结果为 -1
  • 文件读取结束：同样返回 -1

因此，二者会产生冲突

# 为什么使用 int？

int 可以使用 0～255 表示读取到的字节，并使用 -1 表示文件结束

假设文件中存在字节 11111111：

  • 正常读取：返回 00000000 00000000 00000000 11111111，即十进制 255
  • 文件读取结束：返回 -1，其 32 位补码表示为 11111111 11111111 11111111 11111111

因此，可以准确区分实际数据和文件结束标志

# 代码示例

java 
try (FileInputStream input = new FileInputStream("test.txt")) {
    int data;

    while ((data = input.read()) != -1) {
        System.out.println(data);
    }
}

总结：read() 返回 int 并不意味着每次读取 4 个字节，而是为了完整表示单字节的 0～255，同时保留 -1 作为文件结束标志

# BIO、NIO、AIO的区别

BIO、NIO、AIO 是 java 中常见的 3 种 IO 模型，三者的区别：

  • BIO：blocking IO，阻塞，read 调用后会一直阻塞，直至读取完成
  • NIO：new IO，同步非阻塞 IO，一个线程监听多个 channel ，就绪时进行后续的处理
  • AIO：异步IO，当 IO 完成后执行回调函数即可

# JVM 内存结构

图片源自：https://oss.javaguide.cn/github/javaguide/java/jvm/java-runtime-data-areas-jdk1.8.png

Java 虚拟机（JVM）的运行时数据区域主要分为五部分：

内存区域 线程归属 核心作用
堆 线程共享 存储对象、引用数据类型，字符串常量池也在这里（毕竟是引用数据类型），是GC的主要管理区域
虚拟机栈 线程私有 存储方法调用对应的栈帧，如：局部变量等
本地方法栈 线程私有 为本地方法提供支持
程序计数器 线程私有 记录当前线程执行的字节码指令位置
方法区 线程共享 存储类的原数据、运行时常量池等

栈帧：栈的基本单位，每调用一个 java 方法，JVM 就会为该方法创建一个栈帧，用于存储该方法所需的数据

需要注意：

  • 每个线程都有自己的虚拟机栈、程序计数器等线程私有空间，线程结束后，相应的运行时空间也会被释放
  • 堆由线程共享，对象通常分配在堆中，但存在逃逸分析等优化情形
  • 方法区是逻辑概念，在 HotSpot JVM 中，JDK 8 起主要使用元空间（Metaspace）实现，元空间使用本地内存，不属于 Java 堆

# 堆与栈的区别

java 
public void test() {
    int age = 20;
    Person person = new Person();
}

按照常见情况理解：

  • age：栈，基本类型局部变量，其值存放在栈帧的局部变量表中
  • person：局部引用变量，存放在栈帧的局部变量表中
  • new Person()：堆，创建的对象通常存放在堆中

栈主要管理方法执行过程，存放局部变量等，堆主要存储对象实例等引用数据类型

# GC 垃圾回收

为什么需要 GC 垃圾回收？

堆中的数据需要处理，在栈中，出栈后数据会进行删除，但栈存放的是局部变量，而堆中存放的是引用数据类型，如：对象，此时栈中只会清理局部变量，堆中的对象等还没有处理，因此需要GC对堆中的数据进行清理

GC（Garbage Collection）即垃圾回收，负责自动识别并回收不再使用的对象，减少手动管理内存的负担。

# 堆内存分代结构

传统分代垃圾回收将 Java 堆划分为两个主要区域：

  • 新生代（Young Generation）：主要存储新创建的对象，生命周期通常较短
  • 老年代（Old Generation）：主要存储经过多次 GC 后仍然存活的对象

新生代又分为三个区域：

  • Eden（伊甸园，新生区）：对象通常最先分配的区域
  • Survivor 0（S0）：幸存者区
  • Survivor 1（S1）：幸存者区

# 新生代垃圾回收（Young GC）

新生代采用的经典垃圾回收算法是复制算法（Copying）。

基本流程：

  1. 新创建的对象通常分配在 Eden 区
  2. Eden 空间不足时，可能触发 Young GC
  3. GC 识别仍然存活的对象，将其复制到空闲的 Survivor 区
  4. 清理 Eden 及原 Survivor 区中不再需要的对象
  5. S0 和 S1 轮流充当存活对象复制的目标区域
  6. 对象经过多次 GC 仍然存活，达到一定条件后晋升到 Old 区

为什么使用复制算法？

因为新生代中的对象通常存活率较低，仅需复制少量存活对象，效率较高，同时能够减少内存碎片。

注意：若 Survivor 空间不足，对象也可能提前晋升到老年代，不一定必须经过固定次数的 GC。

# 老年代垃圾回收（Old GC）

老年代主要存储长期存活的对象，这些对象存活率通常较高，因此经典分代模型中通常采用以下算法：

  • 标记-清除（Mark-Sweep）：标记存活对象，清除不可达对象，但容易产生内存碎片
  • 标记-整理（Mark-Compact）：标记存活对象，将其移动到连续空间，再回收剩余内存，减少内存碎片

为什么老年代不适合简单使用新生代的复制方案？

因为老年代对象存活率通常较高，需要复制的对象较多，复制开销较大。

需要注意，具体算法取决于垃圾收集器。例如，传统 Parallel Old 使用标记-整理，旧版 CMS 主要使用标记-清除，G1 则通过 Region 进行对象转移和空间回收。

# 总结

GC的存在是为了解决堆中的数据清理，由于栈区域出栈时会将局部变量等数据进行删除，但栈中引用的对象等存放在堆区域，而堆区域便是由 GC 进行数据清理，清理的逻辑大致是：

  • young区域存放新 new 的对象
  • young区域大致分为三块：E区、S0区、S1区
  • E区满了会触发young GC，进行清理，清理策略是复制，将E区存活的数据放置在空闲的S区，然后清空E区与另一个S区，通过两个S区进行交替工作
  • 当young区多次GC清理，某些对象仍存在时，如：清理6次，仍存活，此时该对象会晋升到OLD区，表示使用频率高，存活率高
  • old区满时触发oldGC，清理策略一般是标记-清楚或者标记-整理

注意：

  • young区空间有限，若清理复制时：S区空间满了，剩余存活对象会提前进入old区
  • 大对象会放置在old区，因为大对象进行复制时开销太大，而old区若采用标记-清楚策略时，不会进行移动，更适合

# GC 如何判断哪些对象需要回收？

核心原理：可达性分析（Reachability Analysis），从 GC Roots 出发，沿着对象引用关系向下查找，无法从 GC Roots 到达的对象，通常就可以被回收。

GC 并不是简单地检查某个变量是否存在，而是判断对象是否仍然存在有效的引用路径。

# GC Roots 主要有哪些？

入门阶段重点掌握以下几类：

GC Roots 来源 说明
栈中的引用 当前活动线程的栈帧中，仍然存活的局部变量、方法参数等引用
静态字段（static） 已加载类的静态字段所引用的对象，通常可以作为可达性分析的起点
活跃线程 JVM 中仍然活跃的线程及其相关引用
JNI 引用 Java 调用本地代码时，本地代码持有的有效引用
JVM 内部引用 类加载器、系统类等 JVM 内部结构持有的相关引用

注意：并不是只有栈和 static 才能影响对象是否被回收。 只要某个对象能够通过引用链从 GC Roots 到达，就可能继续存活。

# 示例：栈引用与 static 引用

java 
class User {
    String name;
}

public class Demo {
    static User global = new User();

    public static void main(String[] args) {
        User a = new User();
        User b = a;

        a = null;

        // 此时对象仍然可以通过 b 访问
        System.out.println(b);

        b = null;

        // 如果该对象不存在其他有效引用路径，
        // 它就具备了被 GC 回收的条件

        global = null;

        // 如果 global 原来引用的对象也不存在
        // 其他有效引用路径，它同样具备被回收的条件
    }
}

结合代码理解：

  • a = null：只是取消 a 对对象的引用，但 b 仍然引用该对象，因此对象仍然可达
  • b = null：如果不存在其他有效引用路径，该对象就可能成为垃圾
  • global = null：取消静态字段对对象的引用；如果没有其他有效引用路径，该对象也可能成为垃圾

这里需要区分两个概念：不可达不等于立即被回收。它只是说明对象具备被回收的条件，具体何时回收由 JVM 决定。

# static 对象为什么通常不会被回收？

例如：

java 
static User global = new User();

只要对应的类仍处于可达状态，且静态字段 global 仍然引用这个对象，那么 GC 就能沿着这条引用路径找到它。

text 
GC Roots
   |
   v
static 字段 global
   |
   v
User 对象

因此，该对象通常不会被当作垃圾回收。不过，static 并不意味着对象永远不会被回收。如果对应的类可以被卸载，或者静态字段不再引用该对象，且没有其他有效引用路径，对象仍然可能被回收。

# 最后总结

可以把 GC 的判断过程理解为：

  1. 找到 GC Roots
  2. 沿着引用关系遍历对象
  3. 能够到达的对象，继续保留
  4. 无法到达的对象，通常具备被回收的条件
  5. JVM 在合适的时机执行实际回收

栈中的有效引用、static 字段等决定了对象是否仍然可达；GC 通过可达性分析判断堆中的对象是否具备回收条件，而不是简单地清理没有被当前方法直接引用的数据
